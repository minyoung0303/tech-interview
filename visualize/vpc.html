08 · VPC / Subnet

VPC
Public과 Private을 가르는 건 라우팅 테이블이다

"인터넷이 되면 Public"은 결과입니다. 정의는 라우팅 테이블에 인터넷 게이트웨이로 향하는 0.0.0.0/0 경로가 있는지입니다. 이 한 줄을 말하면 대부분의 지원자와 즉시 갈립니다.

01

한 층씩 쌓아 보는 3-tier VPC

Web / App / DB로 나누는 3-tier 아키텍처가 그대로 서브넷 3계층으로 대응됩니다. Web/WAS 분리와 같은 이야기를 네트워크에서 하는 것입니다.

01VPC는 클라우드 안에 만드는 논리적으로 격리된 사설 네트워크입니다. CIDR로 IP 대역을 정합니다. /16이면 약 65,000개입니다.

02인터넷과 연결되는 통로가 Internet Gateway입니다. 그리고 IGW로 향하는 경로를 가진 서브넷이 Public Subnet이 됩니다. 여기에 ALB를 둡니다.

03앱은 Private Subnet에 둡니다. ALB만 앱과 통신할 수 있고, 인터넷에서 직접 도달할 경로가 없습니다.

04그런데 앱도 외부 API를 호출하고 패키지를 받아야 합니다. 그래서 NAT Gateway를 Public Subnet에 두고 Private의 아웃바운드를 여기로 보냅니다.

05DB는 한 층 더 안쪽 서브넷에 둡니다. 앱 서브넷에서만 3306으로 접근할 수 있습니다.

06DB 서브넷에는 아예 0.0.0.0/0 경로를 두지 않습니다. 나갈 수도 없으니 데이터 유출 경로가 하나 더 막힙니다.

💡

서브넷은 AZ를 걸칠 수 없습니다.

그래서 계층마다 AZ별로 서브넷을 하나씩 만듭니다. 위 그림에서 각 계층에 CIDR이 두 개인 이유입니다. ALB는 최소 2개 AZ의 서브넷을 요구하고, RDS 서브넷 그룹도 2개 이상 AZ가 필요합니다. "왜 서브넷을 6개나 만드나요?"의 답이 이것입니다.

02

Public과 Private을 가르는 건 이 한 줄이다

서브넷 자체에는 "Public/Private"이라는 속성이 없습니다. 라우팅 테이블에 IGW로 향하는 기본 경로가 있는지가 전부입니다.

Public Subnet 라우팅 테이블

목적지대상
10.0.0.0/16local
0.0.0.0/0igw-0a1b2c

이 한 줄이 Public으로 만듭니다. 지우면 그 순간 Private이 됩니다.

Private Subnet 라우팅 테이블

목적지대상
10.0.0.0/16local
0.0.0.0/0nat-0d4e5f

IGW가 아니라 NAT를 가리킵니다. 나가는 건 되고 들어오는 건 안 됩니다.

"Public Subnet에 EC2를 뒀는데 접속이 안 됩니다. 왜죠?"

Public Subnet이어도 인스턴스에 Public IP(또는 EIP)가 없으면 인바운드가 불가능합니다. 인터넷에서 들어오려면 세 가지가 모두 필요합니다 — ① 라우팅 테이블의 IGW 경로, ② 인스턴스의 Public IP, ③ Security Group 인바운드 허용. 하나만 빠져도 안 됩니다. 이걸 순서대로 짚으면 트러블슈팅을 아는 사람으로 읽힙니다.

💡

"왜 NAT Gateway가 Public Subnet에 있어야 하나요?"

NAT 자신이 인터넷으로 나갈 수 있어야 하기 때문입니다. NAT를 Private Subnet에 두면 NAT도 인터넷에 못 나가서 아무 의미가 없습니다. 꼬리질문으로 자주 나오고, 답이 짧고 명확해서 점수가 잘 붙습니다.

01두 서브넷의 라우팅 테이블입니다. VPC 내부 통신(local)은 양쪽 다 동일합니다.

02차이는 기본 경로 0.0.0.0/0이 무엇을 가리키는지뿐입니다. IGW면 Public, NAT면 Private입니다.

03그래서 "Public Subnet인데 접속이 안 된다"가 가능합니다. 라우팅 외에 Public IP와 SG도 필요합니다.

04그리고 NAT는 반드시 Public Subnet에 있어야 합니다. 자기가 나갈 수 있어야 남을 내보낼 수 있으니까요.

03

NAT의 핵심은 나갈 수는 있지만 들어올 수는 없다

NAT는 아웃바운드로 시작된 연결의 응답만 돌려줍니다. 외부에서 먼저 시작하는 연결은 돌려줄 매핑이 없어서 버려집니다.

① 앱 → 외부 결제 API (아웃바운드)

앱 (Private)10.0.11.42
NAT Gateway 주소 변환 + 매핑 기록 출발지를 자기 EIP로 바꿈
외부 API 대기 NAT의 IP만 보인다

응답은 매핑을 따라 앱까지 정확히 돌아온다

② 외부 공격자 → 앱 (인바운드)

공격자스캔 시도
NAT Gateway매핑에 없는 연결
앱 (Private)도달 불가

✕ NAT는 인바운드 규칙이 없다. 애초에 이 방향으로 열 수 있는 설정이 없다

방향양방향아웃바운드 단방향
위치VPC에 붙는다 (VPC당 1개)Public Subnet 안 (AZ별 권장)

01Private Subnet의 앱이 외부 결제 API를 호출합니다. 라우팅에 따라 NAT로 갑니다.

02NAT가 출발지 주소를 자기 공인 IP로 바꾸고 매핑을 기록합니다. 이게 NAT(Network Address Translation)입니다.

03외부 API는 NAT의 IP만 봅니다. 응답은 기록된 매핑을 따라 앱까지 정확히 돌아옵니다. 그래서 "나가는 건 된다"입니다.

04이번엔 외부에서 먼저 연결을 시도합니다. NAT에는 이 연결에 대한 매핑이 없습니다.

05버려집니다. NAT에는 인바운드 허용 규칙이라는 개념 자체가 없습니다. "나갈 수는 있지만 들어올 수는 없다"의 구현이 이것입니다.

💡

NAT 비용은 실제 운영에서 자주 문제가 됩니다.

NAT Gateway는 시간당 요금 + 데이터 처리 요금을 받습니다. ECR 이미지 pull, S3 업로드, CloudWatch 로그 전송이 전부 NAT를 지나가면 청구서가 커집니다. 해결은 VPC Endpoint입니다 — S3와 DynamoDB는 Gateway Endpoint(무료), ECR·SSM 등은 Interface Endpoint를 쓰면 트래픽이 AWS 내부에 머물러 비용도 줄고 보안도 좋아집니다.

04

분리하는 이유는 "보안"이 아니라 공격 표면 최소화다

"보안 때문"은 아무 말도 하지 않은 것과 같습니다. 설정은 실수한다는 전제로 설계한다가 진짜 이유입니다.

❌ 전부 Public Subnet

ALB공인 IP
앱 서버공인 IP
MySQL공인 IP · 3306

방어선이 Security Group 하나뿐입니다. SG를 0.0.0.0/0으로 여는 실수 한 번에 DB가 인터넷에 열립니다.

그리고 실제로 이 사고는 계속 일어납니다.

✅ 계층별 분리 + SG 체인

ALB SG소스: 0.0.0.0/0 · 443
App SG소스: ALB SG · 8080
DB SG소스: App SG · 3306

소스를 IP가 아니라 Security Group으로 지정합니다. 오토 스케일링으로 IP가 바뀌어도 규칙이 그대로 유지됩니다.

여기에 라우팅 경로 자체가 없다는 층이 하나 더 있습니다. SG를 실수로 열어도 인터넷에서 도달할 길이 없습니다.

01공격 표면 최소화 — 인터넷에서 도달 가능한 대상을 ALB로 줄인다
02다층 방어(defense in depth) — ① SG ② NACL ③ 라우팅 경로 없음. 한 층이 뚫려도 다음 층이 있다
03침해 확산 차단 — ALB가 뚫려도 앱으로, 앱이 뚫려도 DB로 가려면 SG와 라우팅을 또 통과해야 한다
04명시적 접근 제어 — SG 체인이 곧 아키텍처 문서가 된다. "누가 누구에게 말할 수 있나"가 코드로 남는다
05아웃바운드 통제 — 나가는 트래픽이 NAT 한 곳으로 모이므로 관측하고 제한할 수 있다

01왼쪽은 전부 Public Subnet에 둔 구성입니다. 동작은 합니다.

02그런데 방어선이 Security Group 하나뿐입니다. 그 한 겹이 실수로 열리면 DB가 인터넷에 노출됩니다.

03"설마 그런 실수를"이 아니라 실수는 일어난다고 전제하는 게 보안 설계입니다.

04오른쪽은 계층을 나누고 SG의 소스를 다른 SG로 지정합니다. IP 대역이 아니라 논리적 그룹으로 연결합니다.

05여기에 라우팅 경로가 없다는 층이 더해집니다. 이유 5개를 이 순서로 말하면 "보안 때문"보다 훨씬 구체적입니다.

05

SG는 stateful, NACL은 stateless

거의 항상 이어서 물어봅니다. 핵심은 "응답 트래픽을 자동으로 허용하는가"입니다.

Security Group (stateful) · ENI 단위

인바운드443 허용 규칙 있음
응답 아웃바운드규칙이 없어도 자동 허용

연결 상태를 기억합니다. 인바운드를 허용하면 그 응답은 자동으로 나갑니다. 그래서 규칙이 단순합니다. 그리고 allow만 쓸 수 있습니다 — deny 규칙이 없습니다.

Network ACL (stateless) · 서브넷 단위

인바운드443 허용 규칙 있음
응답 아웃바운드규칙이 없으면 차단
그래서 필요임시 포트 1024–65535 아웃바운드 허용

상태를 기억하지 않아서 양방향을 각각 열어야 합니다. 대신 deny 규칙을 쓸 수 있어서 특정 IP 차단에 유용합니다.

Security GroupNetwork ACL
적용 대상인스턴스 / ENI서브넷
상태Stateful — 응답 자동 허용Stateless — 각각 허용 필요
규칙allow만allow + deny 가능
평가 방식모든 규칙을 합쳐서 판단번호 순서대로, 먼저 매칭되면 종료
기본값인바운드 전부 거부 / 아웃바운드 전부 허용기본 NACL은 전부 허용
소스 지정IP 대역 또는 다른 SGIP 대역만
주 용도일상적인 접근 제어특정 IP 차단, 서브넷 광역 통제

01둘 다 방화벽인데 붙는 위치가 다릅니다. SG는 인스턴스(ENI)에, NACL은 서브넷에 붙습니다.

02SG는 stateful입니다. 443 인바운드를 허용하면 그 응답은 아웃바운드 규칙이 없어도 자동으로 나갑니다.

03NACL은 stateless입니다. 응답도 아웃바운드 규칙을 통과해야 하고, 응답은 임시 포트로 오가므로 1024–65535를 열어야 합니다. 이래서 관리가 번거롭습니다.

04그래서 실무에서는 SG를 주로 쓰고 NACL은 기본값으로 둡니다. NACL은 특정 IP를 차단할 때 꺼냅니다 — SG에는 deny가 없으니까요.

💡

"SG에서 특정 IP를 차단해주세요" — 할 수 없습니다.

SG는 allow 목록이라서 "이것만 빼고 전부 허용"이 불가능합니다. 그 요구가 오면 NACL의 deny 규칙이나 WAF를 씁니다. 이 질문은 SG/NACL 차이를 정말 이해했는지 확인하는 좋은 지표라서 꽤 자주 나옵니다.

06

서브넷은 AZ에 묶인다 — 그래서 NAT도 AZ마다

비용을 아끼려고 NAT를 한 AZ에만 두면, 그 AZ가 죽을 때 다른 AZ의 아웃바운드가 함께 끊깁니다.

AZ-a

NAT Gateway10.0.1.0/24
앱 파드10.0.11.0/24

AZ-c

NAT Gateway10.0.2.0/24 · 추가
앱 파드10.0.12.0/24
평시: AZ-c의 앱도 AZ-a의 NAT를 경유한다 (비용 절약) AZ-a 장애 발생 AZ-c 앱은 살아 있는데 외부 호출이 전부 실패 AZ마다 NAT를 두면 격리된다 — 비용 vs 가용성

AZ 장애는 "그 AZ만" 죽는 게 아닙니다.

공유 자원이 그 AZ에 있으면 다른 AZ까지 함께 무력화됩니다. NAT Gateway가 대표적이고, 같은 패턴으로 단일 AZ에만 있는 Redis, Multi-AZ가 아닌 RDS도 마찬가지입니다. "멀티 AZ로 구성했다"고 말할 때 공유 자원까지 이중화했는지가 실제 기준입니다.

01NAT Gateway는 시간당 과금이라 하나만 두고 두 AZ가 함께 쓰는 구성이 흔합니다. 비용은 절반입니다.

02AZ-a에 장애가 발생합니다. 여기 있던 NAT도 함께 사라집니다.

03AZ-c의 앱은 멀쩡히 살아 있습니다. 그런데 라우팅이 죽은 NAT를 가리키고 있어서 외부 API 호출과 이미지 pull이 전부 실패합니다. 멀티 AZ의 의미가 없어졌습니다.

04AZ마다 NAT를 두고 각 AZ의 Private 서브넷이 같은 AZ의 NAT를 쓰게 하면 장애가 격리됩니다. 비용과 가용성의 트레이드오프이고, 이 판단을 설명할 수 있는 게 중요합니다.

07

Private에 있는 DB에 어떻게 접속하나

"인터넷에서 도달 불가"로 만들어놨으니 개발자도 못 붙습니다. 이걸 어떻게 푸는지가 실무 질문으로 자주 나옵니다.

① Bastion Host (전통적)

내 노트북
BastionPublic Subnet · 22번 포트
RDSPrivate

단점: 22번 포트가 인터넷에 열려 있고, SSH 키를 관리해야 하고, Bastion 자체가 항상 떠 있어야 하고, 접속 감사 로그가 남지 않습니다.

② SSM Session Manager (요즘 정석)

내 노트북
SSM 엔드포인트AWS API · IAM 인증
Private EC2SSM Agent가 바깥으로 연결
RDS

인바운드 포트를 하나도 열지 않습니다. 에이전트가 아웃바운드로 연결하기 때문입니다. IAM으로 권한을 관리하고, 모든 세션이 CloudTrail·S3에 기록됩니다. 

# RDS까지 포트 포워딩 (Bastion 없이)
aws ssm start-session --target i-0abc123 \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["mydb.xxxx.rds.amazonaws.com"],"portNumber":["3306"],"localPortNumber":["13306"]}'

# 이제 로컬 13306 으로 붙으면 된다
mysql -h 127.0.0.1 -P 13306 -u app -p

01전통적인 방법은 Bastion(점프 서버)입니다. Public Subnet에 서버를 하나 두고 그걸 거쳐 들어갑니다.

02문제는 22번 포트를 인터넷에 열어야 한다는 것입니다. 공격 표면을 줄이려고 Private을 만들었는데 구멍을 하나 낸 셈입니다.

03요즘 정석은 SSM Session Manager입니다. 에이전트가 안에서 밖으로 연결하므로 인바운드 포트를 열지 않습니다. IAM으로 권한을 주고 세션이 전부 기록됩니다.

04포트 포워딩으로 로컬에서 RDS에 바로 붙을 수 있습니다. "Private DB에 어떻게 접속하나요"에 이 답을 하면 확실히 다릅니다.

정리

이 7장면을 한 문단으로

VPC는 클라우드 안에 만드는 논리적으로 격리된 사설 네트워크이고, CIDR로 대역을 정하고 AZ 단위 서브넷으로 나눕니다. Public과 Private을 가르는 건 물리적인 게 아니라 라우팅 테이블에 IGW로 향하는 0.0.0.0/0이 있는지입니다. 분리하는 이유는 공격 표면 최소화입니다 — 노출이 필요한 ALB와 NAT만 Public에 두고 앱과 DB는 Private에 둬서 인터넷에서 도달할 경로 자체를 없앱니다. Private의 아웃바운드는 NAT Gateway를 경유해 "나갈 수는 있지만 들어올 수는 없는" 상태를 만듭니다. 방화벽은 SG(ENI 단위·stateful·allow만)와 NACL(서브넷 단위·stateless·deny 가능) 두 겹이고, SG 소스를 다른 SG로 지정하는 게 실무 방식입니다. 그리고 서브넷은 AZ에 묶이므로 NAT까지 AZ마다 둬야 멀티 AZ가 실제로 동작합니다.

자주 하는 실수

  • "Public은 인터넷이 되고 Private은 안 된다"로만 말한다 → 라우팅 테이블이 정의다
  • 분리 이유를 "보안 때문"이라고만 한다 → 공격 표면 최소화 · 침해 확산 차단 · 다층 방어로 구체화
  • NAT Gateway를 언급하지 않는다 → Private 서버가 패키지 설치나 외부 API를 어떻게 하는지 설명이 안 된다
  • NAT가 Public Subnet에 있어야 하는 이유를 모른다 → 짧고 명확한 꼬리질문이라 자주 나온다
  • SG와 NACL 차이를 모른다 → stateful / stateless가 핵심
  • SG에 deny 규칙이 있다고 생각한다 → allow만 있다
  • 서브넷이 AZ를 걸칠 수 있다고 생각한다 → 못 한다. 그래서 서브넷을 여러 개 만든다
  • Public Subnet이면 무조건 접속된다고 생각한다 → Public IP와 SG도 필요하다
