배포
롤링 업데이트만으로는 무중단이 아니다

이 질문의 성격을 정확히 알아야 합니다. 새로운 요구가 아니라 이력서 검증 질문입니다. 그래서 정답은 교과서적 파이프라인이 아니라 내가 실제로 한 것을 순서대로 말하는 것입니다. 골격은 다섯 단어로 외웁니다 — 소스 → 빌드 → 이미지 → 배포 → 검증.

01

파이프라인 5단계 — 각 단계에서 무엇을 검증하는지가 핵심이다

"git push하면 배포된다" 수준으로 말하면 아무것도 전달되지 않습니다. 단계마다 무엇을 확인하고, 실패하면 어디서 멈추는지를 말해야 합니다.

1 소스 — push → PR → 리뷰 → main 머지 → Webhook으로 CI 트리거
2 빌드 & 검증 — 의존성 캐시 복원 → 린트(golangci-lint) → 테스트(go test -race ./...) → 바이너리 빌드
※ 여기서 실패하면 즉시 중단. 배포 단계로 넘기지 않는다
3 이미지 — 멀티 스테이지 빌드 → 커밋 SHA + 시맨틱 버전으로 태그 → 취약점 스캔(Trivy) → ECR push
4 배포 — staging 배포 → 스모크 테스트 → production 배포(롤링/블루그린/카나리) → 헬스 체크 통과 후 트래픽 유입
5 검증 — 헬스 체크 → Sentry 에러율 / Grafana 지표 / CloudWatch 로그 → 이상 시 롤백

01트리거는 main 머지입니다. 여기서부터 사람 손이 떨어집니다.

02린트와 테스트가 게이트 역할을 합니다. 실패하면 여기서 끝입니다.

03이미지를 만들고 태그를 붙입니다. 태그 전략이 다음 두 장면의 주제입니다.

04staging을 먼저 거칩니다. production은 헬스 체크를 통과한 뒤에 트래픽을 받습니다.

05배포 완료가 끝이 아니라 "이상 없음 확인"이 끝입니다.

💡

절대 원칙: 아는 것만 말하고, 모르는 건 모른다고 합니다.

배포 질문은 꼬리질문 밀도가 가장 높습니다. "ArgoCD로 GitOps 했습니다"라고 하면 바로 sync wave와 drift 감지를 물어봅니다. 이렇게 선을 그으면 면접관은 그 선 안에서 질문하고, 통제 가능한 상황이 됩니다.

"제가 직접 구성한 건 GitHub Actions 기반 파이프라인이고,
 쿠버네티스 환경은 사용해본 경험은 없어서 개념 수준으로만 알고 있습니다."

02

멀티 스테이지 빌드 — 800MB → 20MB

이미지가 작으면 push/pull이 빠르고, 그게 곧 배포 속도입니다. 그리고 보안 이득이 더 큽니다.

— 840 MB
golang:1.23-alpine
(빌드 스테이지)
— 18 MB
alpine:3.20
(최종 이미지)
빌드 스테이지: 컴파일러 + 소스 + 빌드 도구 이걸 그대로 배포하면 840MB 런타임 스테이지에는 바이너리만 복사 → 18MB 최종 이미지에 소스와 컴파일러가 남지 않는다 = 공격 표면 축소

01빌드에는 Go 컴파일러, 모듈 캐시, 소스 코드가 다 필요합니다.

02그 이미지를 그대로 배포하면 800MB가 넘습니다. 노드마다 이걸 내려받습니다.

03런타임 스테이지에는 컴파일된 바이너리만 복사합니다.

04크기보다 중요한 건 소스 코드와 빌드 도구가 남지 않는다는 점입니다.

# ---------- build stage ----------
FROM golang:1.23-alpine AS builder
WORKDIR /app

# 의존성 파일만 먼저 복사한다.
# 소스가 바뀌어도 go.mod/go.sum이 그대로면 이 레이어 캐시가 재사용된다.
COPY go.mod go.sum ./
RUN go mod download

COPY . .

# CGO_ENABLED=0 → 정적 링크. -ldflags "-s -w" → 디버그 심볼 제거로 크기 축소
RUN CGO_ENABLED=0 GOOS=linux go build \
    -ldflags="-s -w -X main.version=${VERSION}" \
    -o /app/server ./cmd/server

# ---------- runtime stage ----------
FROM alpine:3.20

# HTTPS 호출을 위한 CA 인증서, 로그 타임스탬프를 위한 타임존
RUN apk add --no-cache ca-certificates tzdata && \
    adduser -D -u 10001 appuser

WORKDIR /app
COPY --from=builder /app/server .

USER appuser        # root로 실행하지 않는다 (컨테이너 보안 기본)
EXPOSE 8080
ENTRYPOINT ["/app/server"]   # ★ exec 형식. shell 형식이면 SIGTERM을 못 받는다
💡

레이어 캐시 순서 하나로 CI 시간이 몇 분씩 차이납니다.

Docker는 레이어 단위로 캐시합니다. 자주 바뀌는 것을 뒤에 둬야 합니다. COPY . .를 맨 앞에 두면 소스 한 글자만 바뀌어도 go mod download부터 다시 합니다.

03

latest 태그를 쓰면 롤백할 대상이 사라진다

작지만 면접에서 확실히 먹히는 포인트입니다. 핵심 이유는 하나 — 커밋 SHA를 태그로 쓰면 이미지 ↔ 소스 코드가 1:1로 대응됩니다.

myapp:latest

latest → 커밋 a3f9c21
latest → 커밋 7b2e004 이전 latest는 덮어써져 사라졌다
롤백? → 되돌릴 태그가 없다
  • 어떤 버전이 돌고 있는지 알 수 없다 → 장애 시 원인 커밋 특정 불가
  • imagePullPolicy와 엉킨다 — 태그가 같으면 노드가 캐시된 이미지를 그대로 쓸 수 있어 배포했는데 코드가 안 바뀌는 현상이 생긴다
  • 같은 태그가 다른 내용을 가리키므로 재현이 불가능하다

myapp:a3f9c21 (커밋 SHA)

a3f9c21 → 커밋 a3f9c21
7b2e004 → 커밋 7b2e004 둘 다 레지스트리에 남아 있다
롤백 → a3f9c21로 다시 배포 
docker build \
  -t myapp:$(git rev-parse --short HEAD) \
  -t myapp:v1.4.2 .
kubectl rollout status deployment/myapp        # 진행 상황
kubectl rollout history deployment/myapp       # 리비전 목록
kubectl rollout undo deployment/myapp          # 직전 리비전으로
kubectl rollout undo deployment/myapp --to-revision=3

01첫 배포. 양쪽 다 같은 이미지를 가리킵니다.

02두 번째 배포. 왼쪽은 latest가 덮어써지며 이전 것이 사라집니다.

03장애가 나서 롤백해야 합니다. 왼쪽은 되돌릴 대상이 없습니다.

04이미지 태그가 커밋 SHA면 해당 SHA로 다시 배포하는 것도 확실한 롤백입니다.

💡

배포를 아는 사람은 항상 롤백을 먼저 생각합니다.

롤백 이야기를 안 하면 "배포해본 적은 있지만 운영해본 적은 없는 사람"으로 읽힙니다.

04

롤링 업데이트 — maxUnavailable: 0이 무중단의 핵심

새 파드가 Ready가 된 뒤에야 구 파드를 내립니다. 그래서 처리 용량이 절대 줄지 않습니다.

사용 가능한 용량
4 / 4
v1 파드 4개 · 전부 Ready v2 파드 1개 생성 (maxSurge: 1 → 최대 5개까지 허용) v2가 Ready → 그 다음에 v1 하나를 내린다 교체 중 — 구 버전과 신 버전이 동시에 존재한다 v2 4개 완료. 용량은 한 번도 4 미만으로 내려가지 않았다 maxSurge: 0, maxUnavailable: 1 이면? 용량이 3으로 떨어진다 
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1         # 목표보다 최대 1개 더 띄울 수 있다 (최대 5개)
      maxUnavailable: 0   # 사용 불가 파드를 0개로 → 용량이 절대 줄지 않는다

01v1 파드 4개가 트래픽을 받고 있습니다.

02v2 파드 하나를 추가로 띄웁니다. 아직 v1은 4개 그대로입니다.

03v2가 Ready가 되고 나서야 v1 하나를 종료합니다. 순서가 중요합니다.

04이 구간에서 두 버전이 같은 DB를 동시에 바라봅니다. 07장면의 전제입니다.

05교체 완료. 용량 그래프가 한 번도 아래로 내려가지 않았습니다.

06반대 설정이면 리소스는 안 늘지만 처리 용량이 일시적으로 줍니다.

하지만 이 설정만으로는 무중단이 아닙니다.

헬스 체크(readinessProbe) + graceful shutdown이 없으면 롤링 업데이트도 무중단이 아닙니다. Ready 판정이 부정확하면 준비 안 된 파드로 트래픽이 가고, 종료 처리가 부정확하면 진행 중인 요청이 502로 끊깁니다. 다음 두 장면이 그 이야기입니다.

Probe 3종 — liveness에 DB 체크를 넣으면 연쇄 장애가 난다

이 구분을 설명하면 확실히 깊이가 인정됩니다. readiness는 트래픽만 차단, liveness는 컨테이너를 재시작합니다.

트래픽만 빠지고 프로세스는 살아 있습니다. DB가 회복되면 readiness가 다시 통과하고 즉시 트래픽을 받습니다. 재시작 비용이 0입니다.

01startupProbe — 부팅이 느린 앱의 유예 시간. 이게 성공할 때까지 다른 probe는 시작되지 않습니다.

02readinessProbe — 실패하면 Service 엔드포인트에서 제거됩니다. 재시작은 안 합니다.

03livenessProbe — 실패하면 컨테이너를 재시작합니다. 그래서 여기에 넣는 게 위험합니다.

04DB가 흔들리자 왼쪽은 전 파드가 동시에 재시작됩니다.

05오른쪽은 트래픽만 빠집니다. DB 회복 후 즉시 복귀합니다.

containers:
  - name: app
    image: 123456789.dkr.ecr.ap-northeast-2.amazonaws.com/myapp:a3f9c21

    # 부팅이 느린 앱을 위한 유예 시간
    startupProbe:
      httpGet: { path: /healthz, port: 8080 }
      failureThreshold: 30
      periodSeconds: 2        # 최대 60초까지 기다려준다

    # "트래픽 받을 준비가 됐나" → 실패하면 Service 엔드포인트에서 제거 (재시작 안 함)
    readinessProbe:
      httpGet: { path: /readyz, port: 8080 }   # DB ping, Redis ping
      periodSeconds: 5
      failureThreshold: 3

    # "죽었나" → 실패하면 컨테이너를 재시작한다. 가볍게 유지한다
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }   # return 200 수준
      periodSeconds: 10
      failureThreshold: 3

    resources:
      requests: { cpu: 100m, memory: 128Mi }   # 스케줄링 기준. 이만큼은 보장받는다
      limits:   { cpu: 500m, memory: 512Mi }   # 초과 시 CPU는 스로틀, 메모리는 OOMKilled
💡

Go 앱이면 GOMEMLIMIT을 memory limit의 80~90%로 맞춰줍니다.

GC가 미리 동작해서 OOM을 피할 수 있습니다. 메모리 limit을 넘으면 컨테이너가 OOMKilled되고, 이게 CrashLoopBackOff의 흔한 원인입니다. 디버깅은 kubectl describe pod → kubectl logs --previous → 종료 코드 확인 순서입니다.

06

무중단 배포인데 502가 난다면 — 원인은 엔드포인트 전파 지연이다

파드 종료 시 엔드포인트 제거와 SIGTERM이 동시에 일어납니다. 이 문제를 알고 있으면 실무 경험자로 읽힙니다.

파드 Terminating
엔드포인트 제거 요청
+ SIGTERM 전송
kube-proxy · ALB로
전파 (수 초)
전파 완료

❌ preStop 없음

앱이 SIGTERM을 받고 즉시 종료합니다. 그런데 ALB는 아직 이 파드로 라우팅하고 있습니다.

→ 그 사이 도착한 요청이 502로 실패

✅ preStop으로 인위적 지연

lifecycle:
  preStop:
    exec:
      command: ["sleep", "10"]
# 엔드포인트 전파를 기다린다.
# 그 사이엔 요청을 정상 처리한다
terminationGracePeriodSeconds: 45
# preStop(10) + 앱 종료 시간보다 넉넉하게

→ 전파가 끝난 뒤 종료를 시작하므로 502가 사라진다

종료 순서 전체: ① Terminating 전환 → ② 동시에 엔드포인트 제거 + SIGTERM → ③ terminationGracePeriodSeconds(기본 30초) 대기 → ④ 아직 살아있으면 SIGKILL

01파드가 Terminating 상태로 전환됩니다.

02엔드포인트 제거 요청과 SIGTERM이 동시에 나갑니다. 이게 문제의 원인입니다.

03엔드포인트 제거가 kube-proxy와 ALB까지 전파되는 데 수 초가 걸립니다. 그 사이 요청이 옵니다.

04preStop으로 종료를 늦추면 그 시간 동안 요청을 정상 처리합니다.

05그리고 앱 쪽에서도 진행 중인 요청을 마무리하는 graceful shutdown이 필요합니다.

func main() {
   e := echo.New()
   // ... 라우트 등록 ...

   // 서버를 별도 고루틴에서 실행한다 (아래 시그널 대기를 블로킹하지 않도록)
   go func() {
      if err := e.Start(":8080"); err != nil && !errors.Is(err, http.ErrServerClosed) {
         e.Logger.Fatalf("server start failed: %v", err)
      }
   }()

   // SIGTERM(쿠버네티스), SIGINT(로컬 Ctrl+C)를 받는다
   quit := make(chan os.Signal, 1)
   signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
   <-quit

   // 새 요청은 거부하고, 진행 중인 요청은 최대 30초까지 마무리를 기다린다
   ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
   defer cancel()

   if err := e.Shutdown(ctx); err != nil {
      e.Logger.Errorf("graceful shutdown failed: %v", err)
   }

   // 리소스 정리 순서: 서버를 먼저 닫고 나서 DB를 닫는다.
   // 순서를 바꾸면 처리 중인 요청이 DB 접근에서 실패한다.
   if err := db.Close(); err != nil {
      e.Logger.Errorf("db close failed: %v", err)
   }
}

SIGTERM을 아예 못 받는 경우가 있습니다.

Dockerfile에서 ENTRYPOINT를 shell 형식(ENTRYPOINT /app/server)으로 쓰면 쉘이 PID 1이 되어 시그널이 앱에 전달되지 않습니다. 반드시 exec 형식(ENTRYPOINT ["/app/server"])을 씁니다. 이것도 좋은 답변 소재입니다.

07

DB 마이그레이션 — 배포에서 가장 위험한 부분

애플리케이션은 롤백할 수 있지만 스키마 변경은 되돌리기 어렵습니다. 게다가 롤링 중에는 구 버전과 신 버전이 같은 스키마를 동시에 씁니다.

사고 시나리오

1. 코드를 배포하면서 컬럼 이름을 name → full_name으로 변경
2. 롤링 중 구 버전 파드가 아직 name 컬럼을 조회 → 500 에러 폭발
3. 롤백해도 스키마는 이미 바뀌어 있어서 복구가 안 된다

해결: 확장-수축 패턴 (Expand and Contract)

1 EXPAND full_name 컬럼을 nullable로 추가한다. 기존 코드는 영향 없음
2 DUAL WRITE 신규 코드 배포. 쓸 때는 name과 full_name 양쪽에, 읽을 때는 name
3 BACKFILL 기존 데이터를 full_name으로 채운다 (배치로 나눠서)
4 SWITCH 읽기를 full_name으로 전환한 코드를 배포한다
5 CONTRACT 충분히 안정화된 후 name 컬럼을 제거한다

번거롭지만 모든 단계가 롤백 가능합니다. 이게 목적입니다.

01먼저 추가만 합니다. 추가는 기존 코드를 깨지 않습니다.

02양쪽에 쓰기 시작합니다. 아직 읽기는 옛 컬럼이라 롤백이 안전합니다.

03과거 데이터를 채웁니다. 한 번에 다 하지 않고 나눠서 합니다.

04이제 읽기를 새 컬럼으로 옮깁니다. 문제가 생기면 이전 배포로 롤백하면 됩니다.

05마지막에 옛 컬럼을 제거합니다. 여기까지 오면 되돌릴 필요가 없는 상태입니다.

온라인 DDL 주의

-- 상대적으로 안전
ALTER TABLE orders ADD COLUMN memo VARCHAR(255) NULL;  -- INSTANT
ALTER TABLE orders ADD INDEX idx_status (status);       -- INPLACE

-- 위험 (테이블 재생성 + 락)
ALTER TABLE orders MODIFY COLUMN amount BIGINT;
ALTER TABLE orders CHANGE COLUMN name full_name VARCHAR(100);

큰 테이블은 gh-ost나 pt-online-schema-change로 무중단 변경을 합니다. 이름만 알아도 답변에 쓸 수 있습니다.

마이그레이션 실행 위치

권장
K8s Job / initContainer — 애플리케이션 배포 전에 한 번만 실행
위험
앱 시작 시 자동 실행 — 파드가 여러 개면 동시에 실행됩니다. 도구의 DB 락에 의존하게 되므로 권장되지 않습니다
migrate -path ./migrations \
  -database "mysql://user:pass@tcp(host:3306)/db" up
💡

DB 마이그레이션을 언급하는 것만으로도 차별화됩니다.

배포에서 가장 위험한 부분인데 대부분 빼먹습니다. "롤링 중 두 버전이 동시에 도는데 스키마 변경은 어떻게 하나요?"에 확장-수축으로 답할 수 있으면 주니어 중 상위권으로 인식됩니다.

비교

무중단 배포 전략 4가지 — 같은 교체를 다르게 한다

네 방식의 차이는 교체 중에 두 버전을 어떻게 다루는가입니다. 그리고 어떤 방식을 쓰든 헬스 체크 · graceful shutdown · 하위 호환 스키마가 없으면 무중단이 되지 않습니다. 그게 이 장면의 결론입니다.

Recreate 대기
Rolling Update 대기
Blue / Green 대기
LB
Canary 대기
신 버전 트래픽
0%

01출발점은 같습니다. v1 파드 3개가 트래픽을 전부 받고 있고, 이제 v2로 교체해야 합니다.

02Recreate — 전부 내리고 새로 올립니다. 단순하고 리소스도 안 늘지만 그 사이가 다운타임입니다. 무중단이 아닙니다. 두 버전이 절대 공존하면 안 되는 경우(스키마 파괴적 변경)에는 오히려 이걸 씁니다.

03Rolling Update — 하나씩 순차 교체합니다. K8s 기본값이고 추가 리소스가 적습니다. 다만 교체 중에는 v1과 v2가 동시에 트래픽을 받습니다. 그래서 API와 스키마가 하위 호환이어야 합니다.

04Blue/Green — v2 환경을 전체 다 띄운 뒤 LB를 한 번에 스위치합니다. 롤백이 즉시(다시 스위치)이고, 스위치 전에 신 환경만 대상으로 스모크 테스트를 돌릴 수 있습니다. 대가는 리소스 2배입니다.

05Canary — v2 하나에 5%만 보내고 에러율과 p99를 봅니다. 문제없으면 25%, 50%, 100%로 늘립니다. 위험이 가장 작지만 트래픽 분할과 지표 판단 구성이 필요합니다(Argo Rollouts, Flagger).

06그런데 방식 선택보다 중요한 게 전제 조건입니다. readinessProbe·graceful shutdown·preStop·하위 호환 스키마가 없으면 어떤 방식을 써도 502가 납니다. 아래 표와 05·06·07 장면이 그 이야기입니다.

전략방식장점단점
Recreate다 내리고 새로 올린다단순, 리소스 절약다운타임 발생
Rolling Update일부씩 순차 교체추가 리소스 적음, K8s 기본두 버전이 동시에 존재
Blue/Green새 환경 전체를 띄우고 한 번에 스위치롤백이 즉시 (다시 스위치)리소스 2배
Canary소수 트래픽만 신 버전 → 지표 확인 → 점진 확대위험 최소화, 실사용자 검증구성 복잡, 관측 도구 필요

방식보다 중요한 것 — 무중단의 전제 조건

여기가 이 질문의 진짜 승부처입니다. 방식 이름 4개는 누구나 외웁니다.

전제없으면 어떻게 되나
readinessProbe아직 준비 안 된 파드로 트래픽이 가서 502 / 503
Graceful ShutdownSIGTERM 받자마자 죽어서 처리 중인 요청이 끊긴다
preStop + sleep엔드포인트 전파(LB 등록 해제)가 끝나기 전에 죽어서 502 → 06 장면
커넥션 드레이닝종료 중인 서버로 새 요청이 계속 들어온다
하위 호환 스키마구 버전 파드가 없는 컬럼을 조회해서 500 폭발 → 07 장면 확장-수축
멱등성LB나 클라이언트가 재시도할 때 중복 처리 (멱등성 편)
롤백 가능한 이미지 태그latest면 되돌릴 대상이 없다 → 03 장면
💡

Canary와 A/B 테스트는 다릅니다.

Canary는 배포 안전장치이고 A/B 테스트는 제품 실험입니다. 목적이 다릅니다. Canary는 "문제 없나?"를 보고, A/B는 "어느 쪽이 전환율이 높나?"를 봅니다. 이 구분을 짚으면 좋은 가산점입니다.

그리고 무중단 배포의 최종 형태는 Feature Flag로 배포(deploy)와 릴리스(release)를 분리하는 것입니다. 코드는 미리 배포해두고 기능만 플래그로 켭니다. 문제가 생기면 재배포 없이 플래그를 끄면 되므로 롤백이 초 단위가 됩니다. 이 문장을 쓸 수 있으면 답변의 층이 하나 올라갑니다.

설정과 시크릿 관리

원칙: 설정은 코드에서 분리하고, 시크릿은 절대 이미지나 저장소에 넣지 않는다 (12 Factor App).

환경 변수기본. 12 Factor의 권장 방식
K8s ConfigMap비민감 설정 파일/값
K8s Secret민감 값. 단 기본은 base64 인코딩일 뿐 암호화가 아니다
AWS Secrets Manager / Parameter Store자동 로테이션, 감사 로그, IAM 기반 접근 제어
External Secrets OperatorSecrets Manager 값을 K8s Secret으로 자동 동기화

"K8s Secret은 암호화된 건가요?" — 아닙니다. base64 인코딩입니다.

자주 물어보는 함정입니다. etcd 암호화(EncryptionConfiguration)를 켜거나 외부 시크릿 저장소를 써야 한다고 답해야 합니다.

배포 후 무엇을 보나 — 네 가지 골든 시그널

CI 설정 예시 (GitHub Actions)

name: deploy
on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write        # OIDC로 AWS 인증 (액세스 키를 저장소에 안 넣는 방법)

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.23'
          cache: true        # 모듈 캐시로 빌드 시간 단축

      - name: Lint
        uses: golangci/golangci-lint-action@v6
      - name: Test
        run: go test -race -coverprofile=coverage.out ./...

      # 액세스 키 대신 OIDC + IAM Role 사용 (시크릿 유출 위험 제거)
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ap-northeast-2
      - uses: aws-actions/amazon-ecr-login@v2
        id: ecr

      - name: Build and push
        env:
          REGISTRY: ${{ steps.ecr.outputs.registry }}
          TAG: ${{ github.sha }}
        run: |
          docker build -t $REGISTRY/myapp:$TAG .
          docker push $REGISTRY/myapp:$TAG

      - name: Deploy
        run: |
          kubectl set image deployment/myapp app=$REGISTRY/myapp:$TAG
          kubectl rollout status deployment/myapp --timeout=5m
💡

-race와 OIDC 두 개만 챙겨도 인상이 다릅니다.

-race는 Go 테스트에서 데이터 레이스를 잡아주고, CI에 넣어두는 게 관례입니다. OIDC 인증은 액세스 키를 저장소 시크릿에 넣지 않는 방법이라 보안 감각을 보여줄 수 있습니다.

"배포 중에 겪은 문제" 후보 — 하나는 꼭 준비합니다

  • 무중단 배포인데 502가 났다 → graceful shutdown 미구현, preStop 부재 (06장면)
  • 배포했는데 코드가 안 바뀌었다 → latest 태그 + 이미지 캐시 (03장면)
  • 헬스 체크가 401을 반환해서 전체 트래픽이 끊겼다 → 인증 미들웨어 예외 처리 (프록시 편 07장면)
  • 컨테이너가 계속 재시작됐다 → 메모리 limit 초과 OOMKilled, 또는 liveness probe 오설정
  • 환경 변수를 빼먹어서 staging 설정으로 production이 떴다 → 필수 환경 변수 검증 로직 추가
  • CI가 너무 느렸다 → 레이어 캐시 순서 조정, 의존성 캐시 도입

자주 하는 실수

  • 안 해본 걸 해봤다고 말한다 → 배포 질문은 꼬리질문 밀도가 가장 높습니다. 한 번에 무너집니다. 선을 그어 답하는 게 훨씬 안전하고 실제로 더 좋은 평가를 받습니다
  • git push하면 배포된다 수준으로만 말한다 → 각 단계에서 무엇을 검증하는지가 핵심입니다
  • 롤백 이야기를 안 한다 → 배포를 아는 사람은 항상 롤백을 먼저 생각합니다
  • 무중단 배포를 "롤링 업데이트로 합니다"에서 끝낸다 → 헬스 체크 + graceful shutdown이 없으면 롤링 업데이트도 무중단이 아닙니다
  • DB 마이그레이션을 언급하지 않는다 → 배포에서 가장 위험한 부분인데 대부분 빼먹습니다. 여기서 차이가 납니다
