07 · Docker / Container vs VM

컨테이너
가벼운 VM이 아니라, 격리된 프로세스다

"컨테이너는 가벼운 VM"이라고 설명하면 절반만 맞습니다. 핵심은 커널을 공유하는지이고, 컨테이너는 리눅스의 namespace로 격리, cgroup으로 자원 제한을 건 프로세스입니다. 호스트에서 ps를 치면 그냥 프로세스로 보입니다.

01

차이는 딱 하나에서 시작한다 — 커널을 공유하는가

VM은 하이퍼바이저 위에 게스트 OS 전체와 별도 커널을 올립니다. 컨테이너는 호스트 커널을 공유합니다. 크기, 속도, 격리 강도가 모두 여기서 갈립니다.

커널이 하나입니다. 게스트 OS 계층이 아예 없습니다. 그래서 가볍지만 커널을 공유한다는 위험이 남습니다.

컨테이너 이미지에 들어 있는 "OS"는 커널이 아니라 유저 공간 파일들이다 커널 취약점은 호스트 전체에 영향을 준다 그래서 강한 격리가 필요하면 마이크로 VM을 쓴다 
# alpine 이미지 안에 커널이 있는 게 아니다
$ docker run --rm alpine uname -r
6.6.31-linuxkit   ← 호스트 커널 버전이 그대로 나온다

# 호스트에서 보면 컨테이너는 그냥 프로세스다
$ ps -ef | grep server
appuser  21841  ...  /app/server   ← "가상 머신"이 아니다

중간 지점 — 마이크로 VM

AWS Lambda와 Fargate는 Firecracker라는 마이크로 VM 위에서 돕니다. 컨테이너의 속도와 VM의 격리를 동시에 얻으려는 접근이고, 같은 계열로 gVisor, Kata Containers가 있습니다. 이름만 알아도 답변에 쓸 수 있습니다.

01앱 두 개를 격리해서 돌린다는 목적은 같습니다. 구조를 보면 층수가 다릅니다.

02VM은 게스트 OS와 커널을 게스트마다 올립니다. 컨테이너는 그 계층이 없고 호스트 커널 하나를 공유합니다.

03그럼 alpine 이미지 안의 OS는 뭔가요? 커널이 아니라 유저 공간 파일들(libc, 셸, 패키지)입니다. uname -r을 치면 호스트 커널이 나옵니다.

04커널을 공유한다는 건 격리가 VM보다 약하다는 뜻입니다. 커널 취약점으로 컨테이너를 탈출하면 호스트 전체가 영향을 받습니다.

05그래서 남의 코드를 돌리는 멀티테넌시 환경에서는 마이크로 VM을 씁니다. Lambda가 그렇습니다.

💡

"macOS에서 Docker는 왜 느린가요?" — 답이 여기 있습니다.

컨테이너는 리눅스 커널 기능입니다. 그래서 macOS나 Windows의 Docker Desktop은 내부에 리눅스 VM을 띄우고 그 안에서 컨테이너를 돌립니다. 파일 시스템을 VM 경계 너머로 공유하니 볼륨 마운트가 느립니다. 이걸 말하면 개념을 정확히 이해한 것으로 읽힙니다.

02

커널이 없으니 MB 단위, 초 단위가 된다

이 차이가 실무에서 의미하는 건 하나입니다 — 오토 스케일링이 트래픽 스파이크를 따라갈 수 있는가.

VM은 커널 부팅 + init + 서비스 시작을 다 거친다 크기는 그대로 이미지 pull 시간이 된다 멀티 스테이지 빌드로 800MB → 20MB 그래서 스파이크 대응 속도가 다르다 
# ---------- build stage ----------
FROM golang:1.23-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download            # 의존성만 먼저 → 캐시가 살아남는다
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /app/server ./cmd/server

# ---------- runtime stage ----------
FROM alpine:3.20               # 컴파일러도 소스도 남지 않는다
RUN apk add --no-cache ca-certificates tzdata && adduser -D -u 10001 appuser
COPY --from=builder /app/server /app/server
USER appuser                   # root로 실행하지 않는다
ENTRYPOINT ["/app/server"]   # exec 형식 — 06 장면에서 이유를 본다

01VM은 커널 부팅부터 시작합니다. 수십 초에서 분 단위입니다.

02크기도 다릅니다. VM 이미지는 GB, 컨테이너는 MB입니다. 이 크기는 배포할 때마다 이미지 pull 시간으로 돌아옵니다.

03golang 베이스로 그냥 만들면 800MB가 넘습니다. 멀티 스테이지 빌드로 런타임만 남기면 20MB대가 됩니다. 크기만 아니라 보안도 이득입니다 — 최종 이미지에 컴파일러와 소스가 남지 않습니다.

04그래서 컨테이너는 트래픽 스파이크에 초 단위로 대응합니다. VM 기반 오토 스케일링은 늦습니다. Scale-out 이야기와 직접 연결됩니다(스케일 편).

03

격리의 정체 — namespace · cgroup · UnionFS

이 세 단어를 말할 수 있으면 "컨테이너를 안다"에서 "컨테이너를 이해한다"로 넘어갑니다. 모두 리눅스 커널 기능이고, Docker는 그걸 쓰기 쉽게 묶은 도구입니다.

01 namespace — 격리. PID · 네트워크 · 마운트 · 호스트명 · 사용자를 분리해서 컨테이너가 자기만의 세계를 보게 만든다. 컨테이너 안에서 ps를 치면 자기 프로세스만 보인다
02 cgroup — 자원 제한. CPU · 메모리 · I/O 사용량의 상한. 메모리 상한을 넘으면 OOMKilled로 컨테이너가 죽는다
03 UnionFS / OverlayFS — 레이어. 읽기 전용 이미지 레이어 위에 쓰기 가능 레이어를 얹는다(Copy-on-Write). 다음 장면에서 자세히 본다

namespace가 만드는 착각

# 컨테이너 안
$ ps -ef
PID  CMD
  1  /app/server        ← 자기가 1번이라고 믿는다

# 호스트에서 같은 프로세스
$ ps -ef | grep server
PID    CMD
21841  /app/server        ← 실제로는 그냥 프로세스

cgroup을 런타임이 못 읽으면

컨테이너에 limits.cpu: 2를 줬는데 런타임이 호스트 전체 사양(예: 64코어)으로 오인하면 스레드/GC를 과도하게 잡습니다.

Go
GOMAXPROCS를 limit에 맞춘다 (automaxprocs)
JVM
-XX:MaxRAMPercentage 확인
Node
--max-old-space-size

"리소스 limit을 걸었는데 성능이 이상하다"의 흔한 원인입니다.

01namespace가 격리를 만듭니다. 컨테이너는 자기 프로세스만 보고, 자기 네트워크 인터페이스만 보고, 자기 파일시스템만 봅니다.

02cgroup이 자원을 제한합니다. 이게 없으면 한 컨테이너가 호스트 CPU를 다 먹습니다. 메모리 상한을 넘으면 OOMKilled입니다.

03OverlayFS가 레이어를 만듭니다. 이미지를 여러 컨테이너가 공유할 수 있는 이유입니다.

04왼쪽은 namespace가 만든 착각(자기가 PID 1이라 믿는다), 오른쪽은 cgroup을 런타임이 못 읽을 때 생기는 실무 문제입니다.

04

이미지는 불변 레이어, 컨테이너는 그 위의 쓰기 레이어

이미지는 클래스, 컨테이너는 인스턴스입니다. 레이어를 여러 컨테이너가 공유하므로 같은 이미지 100개를 띄워도 디스크가 100배 들지 않습니다.

컨테이너쓰기 가능 레이어 (Copy-on-Write)임시
이미지 L4COPY --from=builder /app/server12MB
이미지 L3RUN go build–
이미지 L2RUN go mod download180MB
이미지 L1FROM alpine:3.207MB
아래에서 위로 쌓인다. 각 명령이 레이어 하나 소스 한 줄만 바꿨다 → 아래 레이어는 캐시 재사용 순서를 뒤집으면 (COPY . . 를 먼저) 의존성부터 전부 다시 받는다 컨테이너가 쓴 데이터는 이 임시 레이어에 있고, 컨테이너와 함께 사라진다 그래서 상태는 볼륨 · S3 · RDS로 뺀다

❌ 캐시가 죽는 순서

COPY . .                ← 소스가 먼저
RUN go mod download
RUN go build
# 소스 한 줄 수정 → 의존성부터 재실행
# 빌드 10초 → 3분

✅ 자주 바뀌는 것을 뒤에

COPY go.mod go.sum ./
RUN go mod download      ← 캐시 유지
COPY . .
RUN go build
# 소스만 바뀌면 위 두 줄은 재사용

레이어는 삭제로 지워지지 않습니다.

RUN rm secret.key를 나중 레이어에서 해도 앞 레이어에는 파일이 그대로 남습니다. 이미지를 받은 사람은 히스토리에서 꺼낼 수 있습니다. 시크릿은 애초에 이미지에 넣지 않고 환경 변수 / Secrets Manager로 주입합니다. 같은 이유로 apt-get install과 rm -rf /var/lib/apt/lists는 한 RUN에 묶어야 크기가 실제로 줄어듭니다.

01Dockerfile의 각 명령이 레이어 하나를 만듭니다. 아래에서 위로 쌓이고, 모두 읽기 전용입니다.

02소스 한 줄을 바꿔 다시 빌드합니다. go.mod가 그대로면 의존성 레이어 캐시가 재사용됩니다.

03순서를 뒤집으면 어떻게 될까요. COPY . .이 먼저면 소스가 바뀔 때마다 그 뒤 레이어가 전부 무효화됩니다. 빌드가 10초에서 3분으로 늘어납니다.

04컨테이너를 실행하면 맨 위에 쓰기 가능 레이어가 얹힙니다. 여기에 쓴 데이터는 컨테이너가 사라지면 없어집니다.

05그래서 컨테이너는 stateless여야 합니다. 파일은 S3, 데이터는 RDS, 로그는 stdout으로 보냅니다.

05

Docker를 쓰는 첫 번째 이유는 환경 일관성이다

"편해서"가 아니라 "내 로컬에서는 되는데요"를 구조적으로 없애기 때문입니다. 이 단어를 답변에 반드시 넣습니다.

❌ 컨테이너 없이

로컬Go 1.23 / macOS / OpenSSL 3.3
CIGo 1.21 / ubuntu-22.04
운영Go 1.20 / Amazon Linux 2 / TZ=UTC

테스트는 통과했고 운영에서만 깨집니다. 타임존이 달라서 날짜 계산이 하루 틀리는 사고가 대표적입니다.

✅ 이미지 하나로

myapp:a3f91c2 Go 1.23 · alpine 3.20 · tzdata · CA certs
로컬CI 스테이징운영

네 곳이 같은 이미지를 돌립니다. 런타임, 시스템 라이브러리, 타임존까지 고정됩니다.

01환경 일관성 — 런타임·라이브러리·타임존까지 이미지에 고정. "로컬에서는 되는데"가 사라진다
02배포 단위 표준화 — 언어가 Go든 Python이든 배포 단위는 이미지 하나. CI/CD·모니터링을 언어와 무관하게 짠다
03즉시 롤백 — 태그가 커밋 SHA면 이전 태그 재배포가 롤백이다. 그래서 latest를 쓰면 안 된다
04빠른 Scale-out — 초 단위 시작. 트래픽 스파이크를 따라간다
05오케스트레이션의 전제 — K8s의 셀프 힐링·오토 스케일링·롤링 업데이트는 컨테이너가 가볍고 언제든 버려도 되는 것이라는 가정 위에 있다
06격리와 이식성 — 한 호스트에서 MySQL 5.7과 8.0을 충돌 없이 돌린다

01로컬은 macOS, Go 1.23입니다.

02CI는 ubuntu에 Go 1.21입니다. 벌써 다릅니다.

03운영은 Amazon Linux, Go 1.20, 타임존도 다릅니다. 테스트는 통과했는데 운영에서만 깨집니다.

04이미지 하나로 통일하면 네 곳이 같은 것을 돌립니다. 이게 환경 일관성입니다.

05그 위에 나머지 이득이 얹힙니다. 1번을 먼저 말하고 3번(롤백)까지 가면 답변이 완성됩니다.

06

ENTRYPOINT 형식 하나로 무중단 배포가 깨진다

shell 형식으로 쓰면 PID 1은 셸이 되고, 셸은 SIGTERM을 앱에 전달하지 않습니다. 앱은 종료 신호를 못 받고 terminationGracePeriodSeconds(기본 30초)가 지나면 SIGKILL로 강제 종료됩니다. 처리 중인 요청은 끊깁니다.

❌ shell 형식

ENTRYPOINT /app/server
# 실제로는 /bin/sh -c "/app/server" 로 실행된다
1PID 1 = /bin/sh, 앱은 자식 프로세스
2kubelet → SIGTERM → PID 1 (셸)
3셸은 자식에게 전달하지 않는다
4앱은 계속 요청을 처리 중… 아무 일도 안 일어남
530초 후 SIGKILL → 강제 종료
!처리 중이던 요청 전부 끊김 → 502

✅ exec 형식

ENTRYPOINT ["/app/server"]
# 앱이 직접 PID 1이 된다
1PID 1 = /app/server
2kubelet → SIGTERM → 앱이 직접 받는다
3새 요청 수신 중단, 헬스체크 실패로 전환
4진행 중인 요청을 끝까지 처리
5DB 커넥션·큐 컨슈머 정리 후 자발적 종료
✓끊긴 요청 0건
// Go / Echo — graceful shutdown
func main() {
    e := echo.New()
    // … 라우팅 …

    go func() {
        if err := e.Start(":8080"); err != nil && err != http.ErrServerClosed {
            e.Logger.Fatal(err)
        }
    }()

    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)   // ← 신호를 받는다
    <-quit

    ctx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
    defer cancel()
    if err := e.Shutdown(ctx); err != nil {          // ← 진행 중 요청을 기다린다
        e.Logger.Error(err)
    }
}

01shell 형식은 실제로 /bin/sh -c로 감싸서 실행됩니다. 그래서 PID 1은 셸이고 앱은 그 자식입니다.

02파드를 종료할 때 kubelet은 PID 1에게 SIGTERM을 보냅니다.

03셸은 그 신호를 자식에게 전달하지 않습니다. 앱은 아무것도 모릅니다.

04앱은 계속 요청을 처리하고 있고, 정리할 기회를 못 얻습니다.

05terminationGracePeriodSeconds가 지나면 SIGKILL이 옵니다. 이건 무시할 수 없습니다.

06결과는 끊긴 요청과 502입니다. exec 형식이면 앱이 직접 신호를 받아 정리하고 나갑니다. 코드는 20줄이면 됩니다.

💡

이건 "무중단 배포인데 502가 났다"의 원인 후보 중 하나입니다.

나머지 후보는 readinessProbe 부재, preStop 부재로 인한 엔드포인트 전파 지연입니다. SIGTERM을 받는 것만으로는 부족해서, LB가 파드를 목록에서 빼는 데 걸리는 수 초를 preStop: sleep 5~15로 벌어줘야 합니다. 자세한 순서는 배포 편 preStop 장면에 있습니다.

07

둘은 대체 관계가 아니다 — 컨테이너는 VM 위에서 돈다

"컨테이너가 VM을 대체했다"고 답하면 감점입니다. 클라우드에서 컨테이너는 거의 항상 VM(EC2) 위에서 돕니다.

AWS 계정 / VPC
EC2 인스턴스 (VM) · EKS 워커 노드 · AZ-a
api-1컨테이너
api-2컨테이너
worker컨테이너
EC2 인스턴스 (VM) · EKS 워커 노드 · AZ-c
api-3컨테이너
api-4기동 중
VM은 노드 단위 격리와 용량을 담당한다 컨테이너는 배포 단위와 밀도를 담당한다 노드가 부족하면 VM을 늘리고(Cluster Autoscaler), 부하가 늘면 파드를 늘린다(HPA)
VM이 여전히 필요한 경우
강한 격리가 필요한 멀티테넌시남의 코드를 돌린다면 커널 공유는 위험하다
다른 OS 커널이 필요Windows 워크로드, 특정 커널 모듈
커널 파라미터를 직접 조정컨테이너는 호스트 커널을 공유하므로 제약이 있다
규제 / 컴플라이언스물리적 분리 수준의 격리 증명이 요구되는 경우

01클라우드 계정 안에 VPC가 있고, 그 안에 서브넷과 인스턴스가 있습니다(VPC 편).

02EKS 워커 노드는 EC2 인스턴스, 즉 VM입니다.

03그 VM 위에 컨테이너(파드)가 여러 개 뜹니다. VM은 용량, 컨테이너는 배포 단위입니다.

04확장도 두 층입니다 — 파드는 HPA로, 노드는 Cluster Autoscaler로 늘립니다. 그래서 "대체"가 아니라 계층입니다.

함정

실무에서 챙기는 것 — 여기서 깊이가 갈린다

항목내용
컨테이너는 stateless로컬 디스크에 파일 저장 금지. 볼륨이나 S3를 쓴다
로그는 stdout으로파일에 쓰면 컨테이너가 죽을 때 사라진다. 수집기가 stdout을 읽는다
1 컨테이너 1 프로세스앱과 Nginx를 한 컨테이너에 넣지 않는다. 사이드카나 Ingress로 분리
root로 실행 금지USER appuser. 컨테이너 탈출 시 피해를 줄인다
latest 태그 금지롤백 대상이 사라지고, 무엇이 떴는지 알 수 없다. 커밋 SHA를 쓴다
멀티 스테이지 빌드800MB → 20MB. 최종 이미지에 컴파일러·소스를 남기지 않는다
PID 1 시그널ENTRYPOINT를 exec 형식으로. 아니면 graceful shutdown이 동작하지 않는다

SSH를 넣지 않기kubectl exec를 쓴다. 컨테이너는 디버깅 대상이 아니라 교체 대상이다
.dockerignore.git, node_modules를 빌드 컨텍스트에서 뺀다. 빌드가 빨라지고 유출을 막는다
💡

Docker와 Kubernetes의 관계도 자주 묻습니다.

Docker는 컨테이너를 만들고 실행하는 도구이고, Kubernetes는 그 컨테이너를 여러 노드에 배치·복구·확장하는 오케스트레이터입니다. 층이 다릅니다. K8s는 1.24부터 dockershim을 제거해서 런타임으로 containerd를 씁니다. 다만 Docker가 만든 이미지는 OCI 표준이라 그대로 돕니다. "Docker를 안 쓰는데 Docker 이미지가 도나요?"라는 질문의 답이 이것입니다.

정리

이 7장면을 한 문단으로

가장 큰 차이는 커널을 공유하는지입니다. VM은 게스트 OS와 커널을 따로 올려서 GB·분 단위지만 격리가 강하고, 컨테이너는 호스트 커널을 공유하면서 namespace로 격리, cgroup으로 제한, OverlayFS로 레이어를 만들어 MB·초 단위가 되지만 격리는 상대적으로 약합니다. Docker를 쓰는 첫 번째 이유는 환경 일관성이고, 거기서 배포 단위 표준화·태그 기반 즉시 롤백·빠른 Scale-out·오케스트레이션이 따라옵니다. 이미지는 불변 레이어, 컨테이너는 그 위의 쓰기 레이어라서 상태는 볼륨·S3·RDS로 빼야 하고, Dockerfile은 자주 바뀌는 것을 뒤에 둬야 캐시가 삽니다. 그리고 ENTRYPOINT를 exec 형식으로 쓰지 않으면 SIGTERM이 앱에 도달하지 않아 무중단 배포가 깨집니다. 마지막으로 컨테이너는 VM을 대체한 게 아니라 VM 위에서 돕니다.

자주 하는 실수

  • "컨테이너는 가벼운 VM"이라고 설명한다 → 격리된 프로세스다. 이 차이가 질문의 핵심
  • "Docker를 쓰면 편해요"로 끝낸다 → 환경 일관성이라는 단어를 반드시 쓴다
  • 컨테이너가 VM을 대체했다고 말한다 → 함께 쓰인다. EKS 노드는 EC2다
  • 격리가 약하다는 단점을 모른다 → 트레이드오프를 아는 게 신뢰를 만든다
  • namespace / cgroup을 모른다 → 이 두 단어가 "이해했다"의 증거다
  • 이미지 안에 커널이 있다고 생각한다 → 유저 공간 파일들이다
  • 레이어 캐시 순서를 모른다 → 매일 체감되는 실무 포인트다
