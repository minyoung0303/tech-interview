프록시
누구를 대신하고, 누구를 숨기는가

"Forward는 나갈 때, Reverse는 들어올 때"로 외우면 헷갈립니다. 기준은 방향이 아니라 누구를 대리하는가이고, 헷갈리면 "숨겨지는 쪽이 누구냐"로 되짚습니다. 이 한 줄만 세우면 뒤 설명이 전부 정리됩니다.

01

둘 다 중개자다. 다른 건 어느 편에 서 있는지다

Forward Proxy는 클라이언트 편에 서서 클라이언트를 대신하고, 서버에게 클라이언트를 숨깁니다. Reverse Proxy는 서버 편에 서서 서버를 대신하고, 클라이언트에게 실제 서버를 숨깁니다.

Forward Proxy

Forward Proxy클라이언트 편
서버 클라이언트를 안다 프록시 IP만 보인다

Reverse Proxy

클라이언트 서버 구성을 안다 프록시만 서버로 안다
Reverse Proxy서버 편
서버 A
서버 B
서버 C
Forward → 숨겨지는 쪽: 클라이언트 Reverse → 숨겨지는 쪽: 서버

01구조상 둘 다 "클라이언트와 서버 사이의 중개자"입니다. 여기까지는 같습니다.

02Forward는 클라이언트가 설정합니다(브라우저 프록시 설정, HTTP_PROXY). Reverse는 서버 운영자가 설정합니다.

03그래서 가려지는 쪽이 반대입니다. Forward는 서버가 클라이언트를 못 보고, Reverse는 클라이언트가 서버 구성을 못 봅니다.

04정리하면 한 줄입니다 — "누구를 대신하고 누구를 숨기는가."

Forward ProxyReverse Proxy

클라이언트 인지안다 (설정해야 하므로)모른다
대표 제품Squid, 사내 프록시, Charles / mitmproxyNginx, ALB, CloudFront, Envoy, Traefik
주 목적접근 통제, 익명성, 캐싱로드밸런싱, TLS 종료, 오리진 은닉
💡

"NAT Gateway는 Forward Proxy인가요?" — 엄밀히는 아닙니다.

NAT는 L3에서 IP 주소만 바꿔주고 HTTP 같은 애플리케이션 계층을 이해하지 못합니다. Forward Proxy는 L7에서 요청 내용을 보고 판단합니다(URL 기반 차단, 캐싱). "아웃바운드를 한 지점으로 모은다"는 효과는 비슷하지만 동작 계층이 다릅니다.

반대로 CDN은 Reverse Proxy입니다. 오리진 서버를 대신하니까요. 이것도 자주 묻습니다.

02

로드 밸런싱과 헬스 체크 — 무중단 배포의 전제 조건

프록시가 주기적으로 백엔드 상태를 확인하고 죽은 서버로는 트래픽을 안 보냅니다. 이게 없으면 롤링 업데이트도 무중단이 아닙니다.

요청 6개
Reverse Proxy 라운드 로빈 라운드 로빈 헬스 체크 실행 중
서버 A요청 0개
서버 B요청 0개
서버 C요청 0개
순서대로 2개씩 균등 분산 서버 C가 헬스 체크 실패 C를 대상 그룹에서 제거 남은 A, B로만 분산 — 사용자는 장애를 모른다

01요청이 프록시로 들어옵니다.

02기본은 라운드 로빈. 순서대로 나눠줍니다.

03서버 C가 헬스 체크에 응답하지 않습니다.

04프록시가 C를 대상에서 빼버립니다. 새 요청은 C로 가지 않습니다.

05사용자 입장에서는 아무 일도 없습니다. 이게 프록시를 두는 이유 중 가장 큰 하나입니다.

알고리즘

Reverse Proxy가 주는 것

  • 로드 밸런싱 + 헬스 체크
  • TLS 종료 (다음 장면)
  • 캐싱 — CDN이 이걸 지리적으로 분산해서 하는 것
  • L7 라우팅 — 경로/호스트/헤더 기반
  • 오리진 은닉 · Rate Limiting · WAF · DDoS 완충
  • 압축(gzip/brotli), 요청 버퍼링, 느린 클라이언트 흡수

마지막 항목이 잘 알려지지 않은 실질적 이득입니다. Nginx가 느린 클라이언트의 요청을 다 받은 뒤 한 번에 백엔드로 넘겨서, 백엔드 워커가 느린 네트워크에 묶이지 않게 합니다.

03

TLS 종료 — 자물쇠는 프록시에서 열린다

HTTPS 복호화를 프록시가 처리하고, 뒤쪽 애플리케이션 서버로는 HTTP로 넘깁니다.

브라우저
🔒 HTTPS
ALB / Nginx인증서 보유
🔓 HTTP
앱 서버TLS를 몰라도 된다
  • 인증서를 한 곳에서만 관리하면 됩니다 (ACM + ALB 조합)
  • 암복호화 CPU 비용을 프록시가 흡수합니다
  • 애플리케이션 코드는 TLS를 몰라도 됩니다
  • 보안 등급이 높은 환경에서는 프록시 뒤 구간도 다시 암호화합니다 — TLS re-encryption / end-to-end TLS

01브라우저 ↔ 프록시 구간은 HTTPS로 암호화됩니다.

02프록시가 복호화한 뒤 내부 구간은 평문 HTTP로 넘깁니다. 이걸 TLS 종료라고 합니다.

03얻는 것 세 가지와, 필요하면 뒤 구간도 다시 암호화하는 옵션입니다.

부작용: 리다이렉트가 http로 나갑니다.

프록시에서 TLS를 종료하면 애플리케이션은 자기가 HTTP로 서비스된다고 생각합니다. 절대 URL로 리다이렉트를 만들면 http://...가 나가서 브라우저 경고나 무한 리다이렉트가 생깁니다. X-Forwarded-Proto를 읽어 스킴을 결정하거나, 가급적 상대 경로 리다이렉트를 씁니다.

L7 라우팅 — HTTP 내용을 이해하기 때문에 가능한 일

경로, 호스트(도메인), 헤더 기반 분기. MSA에서 서비스 진입점이 됩니다.

GET /api/orders GET /admin/users GET /logo.svg

location /api/   { proxy_pass http://backend; }

01/api/로 시작하는 요청은 API 백엔드로 보냅니다.

02/admin/은 다른 서버로. 클라이언트는 서버가 나뉜 걸 모릅니다.

03정적 파일은 백엔드까지 갈 필요 없이 Nginx가 직접 응답합니다.

04설정은 이렇게 몇 줄입니다. L4에서는 이게 불가능합니다.

💡

Reverse Proxy는 기본적으로 L7 개념입니다.

L4는 "로드 밸런서"라고 부르는 게 더 정확합니다. IP/포트만 보고 HTTP 내용을 이해하지 못하므로 경로 기반 라우팅이 불가능합니다. 아래 표에서 정리합니다.

05

X-Forwarded-For는 위조할 수 있다

보안 감각을 보여줄 수 있는 몇 안 되는 지점입니다. 꼭 챙기세요. 프록시 뒤에서 애플리케이션이 보는 원격 주소는 프록시의 IP이고, 원래 정보는 헤더로 전달됩니다.

X-Forwarded-For: 203.0.113.10, 10.0.1.5, 10.0.2.7 ↑ 원 클라이언트    ↑ 프록시1    ↑ 프록시2 — 거칠 때마다 뒤에 추가된다
클라이언트가 처음부터 이렇게 보내면?
X-Forwarded-For: 1.2.3.4, 203.0.113.10, 10.0.1.5 ↑ 클라이언트가 넣은 가짜 — 프록시는 그 뒤에 덧붙일 뿐 검증하지 않는다

❌ 맨 왼쪽 값을 그대로 신뢰

IP 기반 rate limit, 차단, 지역 판별이 전부 우회됩니다. 헤더에 아무 IP나 넣으면 되니까요.

✅ 오른쪽에서 신뢰 프록시 수만큼 세어 들어간다

내가 신뢰하는 프록시 개수를 알고, 오른쪽에서 그만큼 건너뛴 값을 씁니다. 신뢰 프록시가 ALB 1개라면 오른쪽에서 1번째를 건너뛴 값이 실제 클라이언트입니다.

프록시가 전달하는 헤더
X-Forwarded-For원 클라이언트 IP. 거칠 때마다 뒤에 추가된다
X-Forwarded-Proto원래 프로토콜 (https)
X-Forwarded-Host원래 Host 헤더
X-Real-IPNginx에서 관습적으로 쓰는 단일 클라이언트 IP
ForwardedRFC 7239 표준. 위 헤더들을 하나로 합친 형식

01정상적인 XFF는 왼쪽이 원 클라이언트, 오른쪽으로 갈수록 가까운 프록시입니다.

02클라이언트가 처음부터 가짜 값을 넣어 보내면 프록시는 그 뒤에 덧붙일 뿐입니다.

03그래서 맨 왼쪽 값을 믿는 코드는 IP 기반 방어가 전부 무력화됩니다.

04정답은 오른쪽에서 신뢰 프록시 개수만큼 세어 들어가는 것입니다.

05관련 헤더 정리. Forwarded가 표준이지만 실무에서는 XFF가 여전히 주류입니다.

e := echo.New()

// 신뢰할 프록시 대역을 명시한다. 그 대역에서 온 XFF만 신뢰한다.
e.IPExtractor = echo.ExtractIPFromXFFHeader(
   echo.TrustLoopback(false),
   echo.TrustLinkLocal(false),
   echo.TrustPrivateNet(true), // VPC 내부 ALB → 사설 대역 신뢰
)

e.GET("/whoami", func(c echo.Context) error {
   return c.String(200, c.RealIP()) // 위 설정을 반영한 실제 클라이언트 IP
})

설정을 안 하면 모든 요청의 IP가 ALB IP로 기록됩니다.

Echo의 기본값 ExtractIPDirect는 XFF를 아예 무시하고 TCP 연결의 원격 주소를 씁니다. 프록시 뒤에 있으면서 이걸 설정하지 않으면 Sentry나 CloudWatch 로그를 봐도 실제 사용자 IP를 못 찾습니다.

06

타임아웃이 두 겹이다 — 짧은 쪽이 먼저 끊는다

ALB의 idle timeout(기본 60초)이 애플리케이션 타임아웃보다 짧으면 백엔드는 아직 처리 중인데 클라이언트는 504를 받습니다.

ALB idle timeout
60s
앱 처리 시간
90s
요청 시작 — 무거운 리포트 생성 30초 경과. 양쪽 다 진행 중 60초 — ALB가 연결을 끊고 클라이언트에 504 90초 — 앱은 멀쩡히 다 끝냈다. 응답할 곳이 없다

원칙

프록시 타임아웃 ≥ 애플리케이션 타임아웃

Nginx라면 proxy_read_timeout, proxy_connect_timeout, proxy_send_timeout을 앱보다 넉넉하게 잡습니다.

같은 계열의 함정 두 개 더

413
Nginx client_max_body_size 기본값이 1MB. 안 올리고 파일 업로드를 붙이면 앱 코드는 멀쩡한데 413이 납니다
WebSocket
Upgrade 헤더를 넘겨야 하고, proxy_read_timeout이 기본 60초면 연결이 계속 끊깁니다

0190초쯤 걸리는 무거운 요청이 들어옵니다.

02양쪽 타이머가 함께 흐릅니다. 아직 문제없습니다.

03ALB가 60초에 먼저 포기합니다. 클라이언트는 504 Gateway Timeout을 받습니다.

04앱은 90초에 정상 완료했지만 응답을 보낼 연결이 이미 없습니다. 로그만 보면 성공으로 보입니다.

location /ws/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 3600s;   # 기본 60초면 연결이 계속 끊긴다
}
07

배포 직후 전면 장애의 전형적 원인 — 헬스 체크가 401

프록시의 헬스 체크에는 인증 토큰이 없습니다. /healthz가 인증 미들웨어에 걸리면 프록시는 서버가 죽었다고 판단합니다.

ALBGET /healthz
인증 미들웨어 토큰 검사 토큰 없음 → 401
파드 1
파드 2
파드 3
ALB가 /healthz를 호출한다 (토큰 없음) 인증 미들웨어가 401 반환 ALB: "모든 파드가 unhealthy" → 전부 제거 해결: /healthz를 인증에서 제외한다

앱은 전부 정상인데 사용자에게는 503. 코드는 멀쩡하고 설정 한 줄이 원인입니다. 

e.GET("/healthz", health)          // 인증 미들웨어 등록 전에 선언
api := e.Group("/api", authMiddleware) // 인증은 여기서부터

01ALB가 주기적으로 /healthz를 호출합니다. 인증 토큰은 당연히 없습니다.

02인증 미들웨어가 전역으로 걸려 있으면 401을 반환합니다.

03ALB는 200이 아니면 unhealthy로 봅니다. 모든 파드가 대상에서 빠집니다.

04해결은 헬스 체크 엔드포인트를 인증 미들웨어 밖에 두는 것입니다.

💡

"배포했는데 전부 503이 났다"의 원인 후보 1순위입니다.

같은 계열로 헬스 체크 경로가 리다이렉트를 반환하는 경우(301/302도 unhealthy), 헬스 체크에 DB 체크를 넣어서 DB가 흔들릴 때 전체가 빠지는 경우가 있습니다. 뒤쪽은 배포 편 Probe 장면에서 다룹니다.

API Gateway와 Reverse Proxy의 차이

API Gateway는 Reverse Proxy에 인증, rate limit, API 키 관리, 사용량 측정, 스펙 문서화 같은 API 관리 기능이 더해진 상위 개념입니다. "게이트웨이 ⊃ 리버스 프록시"로 이해하면 됩니다.

Kubernetes / AWS에서의 실제 구조

공고 스택이 AWS/EKS라면 이 구조로 설명해야 점수가 붙습니다. Nginx만 말하면 절반입니다.

1사용자
2CloudFront — CDN / 엣지 캐싱. 이것도 Reverse Proxy다
3ALB — L7 로드밸런서, TLS 종료, WAF
4Ingress (ALB Controller) — 규칙 선언일 뿐. 실제 트래픽 처리는 ALB가 한다
5Service (ClusterIP) — L4다. kube-proxy가 파드로 분산. HTTP 내용을 모른다
6Pod → Container — Go/Echo 애플리케이션
  • Ingress는 프록시가 아니라 "규칙 선언"입니다. 실제 프록시 역할을 하는 건 Ingress Controller가 프로비저닝한 ALB(또는 Nginx Ingress Controller의 Nginx 파드)입니다. 이 구분을 하면 이해도가 확실히 드러납니다.
  • ALB Target Type — instance는 노드 포트를 거치고, ip는 파드 IP로 직접 보냅니다. ip 모드가 홉이 하나 줄어 효율적이고 파드 단위 헬스 체크가 정확합니다.
  • Service Mesh (Istio, Linkerd) — 각 파드에 사이드카 프록시(Envoy)를 붙여 서비스 간 통신까지 프록시가 관리합니다. mTLS, 재시도, 서킷 브레이커, 트래픽 분할. 이름과 목적만 알아도 충분합니다.
upstream backend {
    least_conn;
    server 10.0.1.10:8080 max_fails=3 fail_timeout=30s;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=30s;
    keepalive 32;   # 백엔드와 커넥션 재사용. 없으면 매 요청마다 TCP 핸드셰이크
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    client_max_body_size 20m;
    gzip on;

    location / {
        proxy_pass http://backend;
        proxy_http_version 1.1;

        # 원 요청 정보를 백엔드로 전달
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout    65s;   # 애플리케이션 타임아웃보다 길게
    }

    location = /healthz {
        access_log off;
        proxy_pass http://backend;
    }
}
💡

$proxy_add_x_forwarded_for를 쓰는 이유

기존 XFF에 $remote_addr를 덧붙여줍니다. 직접 $remote_addr만 넣으면 앞단 프록시 정보가 사라집니다.

정리

이 7장면을 한 문단으로

둘 다 클라이언트와 서버 사이의 중개자인데, 누구를 대신하고 누구를 숨기는지가 다릅니다. Forward Proxy는 클라이언트 편에 서서 서버에게 클라이언트를 숨기고, Reverse Proxy는 서버 편에 서서 클라이언트에게 실제 서버를 숨깁니다. 백엔드 개발자가 매일 마주치는 건 Reverse Proxy이고, 로드밸런싱·헬스체크·TLS 종료·캐싱·L7 라우팅·오리진 은닉·압축을 줍니다. L4는 IP/포트만 보므로 경로 기반 라우팅이 안 되고(NLB), L7은 HTTP를 이해합니다(ALB). 그리고 프록시 뒤에서 개발할 때는 클라이언트 IP(XFF 위조), 리다이렉트 스킴, 두 겹 타임아웃, 업로드 용량, WebSocket Upgrade, 헬스체크 인증 제외를 챙겨야 합니다.

자주 하는 실수

  • "Forward는 나갈 때, Reverse는 들어올 때"로만 외운다 → 기준은 누구를 대리하는가. 헷갈리면 "숨겨지는 쪽이 누구냐"로 되짚습니다
  • Reverse Proxy를 로드밸런서와 같은 것으로 본다 → 로드밸런싱은 여러 기능 중 하나입니다
  • L4/L7 구분을 못 한다 → 이 질문은 거의 항상 따라옵니다
  • Nginx만 말하고 실무 환경(ALB, CloudFront, Ingress)과 연결하지 못한다
  • XFF 위조 문제를 모른다 → 보안 감각을 보여줄 수 있는 몇 안 되는 지점입니다
