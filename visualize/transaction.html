01

트랜잭션 — 여러 작업을 하나의 논리적 단위로 묶는다

A에서 3,000원을 빼고 B에 3,000원을 넣는다. 둘 중 하나만 되면 돈이 사라집니다. 그래서 두 작업을 하나로 묶고, 실패하면 통째로 되돌립니다.

idle BEGIN ERROR ROLLBACK DONE
A 계좌 10,000원 7,000원 10,000원
B 계좌 0원
1) BEGIN 2) UPDATE A -3,000 3) 💥 여기서 서버가 죽는다 4) undo log로 되돌린다 5) 아무 일도 없던 상태
undo log A.balance = 10,000 (변경 전 값)

01BEGIN. 이 순간부터 커밋 전까지의 변경은 아직 확정이 아닙니다.

02A에서 3,000원 차감. 아직 B에는 안 넣었으니 돈이 공중에 떠 있는 상태입니다.

03여기서 장애가 납니다. 원자성이 없으면 3,000원은 그대로 사라집니다.

04InnoDB는 변경 전 값을 undo log에 미리 적어둡니다. 그걸로 되돌립니다.

05결과는 "부분 성공"이 아니라 "아무 일도 없었음". 이게 원자성입니다.

💡

원자성은 "성공을 보장"하는 게 아니라 "중간 상태를 남기지 않는 것"입니다.

실패는 얼마든지 할 수 있습니다. 실패했을 때 절반만 반영된 상태로 끝나지 않는 게 핵심입니다.

02

ACID — 네 글자를 나열하지 말고, InnoDB가 어떻게 구현하는지 말한다

여기서 점수가 갈립니다. 이름만 아는 사람과 구현 장치를 아는 사람의 차이입니다.

A

Atomicity 원자성

전부 반영 또는 전부 취소

undo log

C

Consistency 일관성

제약 조건이 깨지지 않음

PK / FK / UNIQUE

I

Isolation 격리성

동시 트랜잭션이 서로 간섭하지 않음

MVCC + 락

D

Durability 지속성

커밋된 건 장애가 나도 남는다

redo log (WAL)

COMMIT
redo log디스크에 flush
데이터 파일나중에 (더티 페이지)

커밋이 보장하는 건 redo log의 flush입니다. 데이터 파일에 바로 쓰이는 게 아닙니다.

A원자성 → undo log. 변경 전 값을 적어두고 롤백 시 되돌립니다.

C일관성 → 제약 조건과 트리거. 트랜잭션 전후로 규칙이 깨지지 않습니다.

I격리성 → MVCC + 락. 이 두 개가 격리 수준의 실제 구현체입니다.

D지속성 → redo log(WAL). 장애 시 재시작하면서 redo log를 재생해 복구합니다.

-- 지속성의 강도를 정하는 설정 (꼬리질문 단골)
innodb_flush_log_at_trx_commit = 1  -- 기본. 커밋마다 flush + fsync. 가장 안전/가장 느림
                               = 2  -- OS 버퍼까지만. MySQL이 죽어도 살지만 OS가 죽으면 유실
                               = 0  -- 1초마다. 가장 빠르고 가장 위험
💡

"커밋하면 디스크에 바로 쓰이나요?"에 "네"라고 답하면 반쯤 틀립니다.

데이터 파일이 아니라 redo log가 먼저 디스크로 갑니다. 이게 WAL(Write-Ahead Logging)이고, 순차 쓰기라서 빠릅니다. 데이터 파일 반영은 나중에 천천히 일어납니다.

03

격리 수준은 세 가지 이상 현상을 얼마나 막는지로 정해진다

이상 현상을 먼저 이해하면 격리 수준 표는 자동으로 외워집니다. 순서대로 하나씩 재현합니다.

T1
SELECT balance SELECT balance again SELECT count(*)
T2
UPDATE (미커밋) UPDATE + COMMIT INSERT + COMMIT
시간 →

① Dirty Read — 커밋 안 된 값을 읽는다

T2가 아직 커밋하지 않은 변경을 T1이 읽습니다. T2가 롤백하면 T1은 존재하지 않았던 값으로 판단을 내린 셈이 됩니다.

READ UNCOMMITTED에서만 발생

② Non-Repeatable Read — 같은 행을 두 번 읽었는데 값이 다르다

사이에 T2가 UPDATE 후 커밋했습니다. T1은 한 트랜잭션 안에서 10,000 → 7,000 두 값을 보게 됩니다.

READ COMMITTED까지 발생

③ Phantom Read — 없던 행이 나타난다

같은 조건으로 다시 조회했는데 T2가 INSERT한 행이 끼어 있습니다. 값이 아니라 결과 집합이 바뀝니다.

MySQL RR은 이걸 상당 부분 막는다 →

01T1이 조회하는 사이 T2가 아직 커밋하지 않은 변경을 만듭니다.

02T1이 그 미커밋 값을 읽으면 Dirty Read입니다.

03이번엔 T2가 UPDATE 후 커밋까지 합니다.

04T1이 같은 행을 다시 읽으면 값이 달라져 있습니다 → Non-Repeatable Read.

05T2가 새 행을 INSERT하고 커밋합니다.

06T1이 같은 조건으로 세면 개수가 늘어나 있습니다 → Phantom Read.

격리 수준 4단계 — 위로 갈수록 동시성이 좋고, 아래로 갈수록 안전하다
수준DirtyNon-RepeatablePhantom기본값인 DB
READ UNCOMMITTEDOOO—
READ COMMITTEDXOOPostgreSQL / Oracle
REPEATABLE READXX△MySQL InnoDB
SERIALIZABLEXXX—
💡

MySQL 기본값은 REPEATABLE READ입니다. READ COMMITTED라고 답하면 그건 PostgreSQL/Oracle입니다.

그리고 표의 △가 중요합니다. 표준 스펙상 RR은 팬텀을 허용하지만 InnoDB는 두 장치로 막습니다. 일반 SELECT는 MVCC 스냅샷을 읽어서 새 행이 안 보이고, SELECT ... FOR UPDATE는 갭 락 / 넥스트키 락으로 범위 자체를 잠가 INSERT를 차단합니다.

04

MVCC — 읽기가 쓰기를 막지 않고, 쓰기가 읽기를 막지 않는다

같은 행의 여러 버전을 유지해서 각 트랜잭션이 자기 시점의 버전을 읽습니다. 그래서 락 없이도 일관된 읽기가 됩니다.

모든 행에는 숨은 컬럼이 붙어 있습니다 — DB_TRX_ID DB_ROLL_PTR DB_ROW_ID

balance = 10,000 trx_id 100 · 유일한 버전
— DB_ROLL_PTR → NULL
balance = 7,000 trx_id 205 · 최신
— DB_ROLL_PTR →
balance = 10,000 trx 100 · undo log
→
balance = 12,000 trx 88 · undo log
T1의 ReadView 내가 볼 수 있는 trx: < 200
balance = 10,000 trx 205는 안 보임 → 체인을 거슬러 올라가 trx 100 버전을 읽는다

01처음엔 버전이 하나입니다. DB_TRX_ID가 마지막 변경 트랜잭션을 가리킵니다.

02UPDATE하면 이전 버전이 undo log로 밀려나고 DB_ROLL_PTR로 연결됩니다.

03UPDATE가 반복되면 버전 체인이 길어집니다. 여기가 MVCC의 비용 지점입니다.

04읽는 쪽은 ReadView를 만듭니다. "내가 볼 수 있는 트랜잭션 ID 집합"입니다.

05볼 수 없는 버전이면 체인을 거슬러 올라가 볼 수 있는 가장 최신 버전을 찾습니다.

MVCC의 단점 = 긴 트랜잭션이 운영 DB를 망가뜨리는 경로

오래 열려 있는 트랜잭션이 있으면, 그 트랜잭션이 봐야 하는 옛 버전들을 지울 수 없습니다. undo 영역이 계속 커지고(History list length 증가), 버전 체인이 길어져 읽기도 느려집니다. purge 스레드가 정리하려 해도 긴 트랜잭션이 막습니다. 배치나 리포트용 긴 트랜잭션이 대표적인 원인입니다.

05

READ COMMITTED와 REPEATABLE READ의 차이는 딱 한 줄이다

ReadView를 언제 만드느냐. 이 한 줄이 두 격리 수준의 모든 동작 차이를 설명합니다. 같은 시나리오를 나란히 돌려봅니다.

READ COMMITTED — SELECT마다 새 ReadView

1차 SELECT — 10,000
T2가 7,000으로 UPDATE + COMMIT
2차 SELECT — 7,000

값이 바뀌었다 → Non-Repeatable Read 발생

REPEATABLE READ — 첫 읽기 때 만든 ReadView를 끝까지 재사용

1차 SELECT — 10,000
T2가 7,000으로 UPDATE + COMMIT
2차 SELECT — 10,000

같은 스냅샷을 계속 읽는다 → 반복 읽기 일관성

01같은 트랜잭션 안에서 같은 행을 두 번 읽는 시나리오입니다.

021차 SELECT. 양쪽 다 10,000을 읽습니다. 여기까지는 같습니다.

03중간에 T2가 7,000으로 바꾸고 커밋합니다. 2차 SELECT의 결과가 갈립니다.

04차이의 원인은 격리 수준 이름이 아니라 ReadView 생성 시점입니다.

-- 확인 / 변경
SELECT @@transaction_isolation;         -- 현재 세션
SELECT @@global.transaction_isolation;  -- 전역
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
💡

"ReadView를 SELECT마다 만드는가, 트랜잭션 첫 읽기에 한 번 만드는가."

이 문장을 말하면 깊이가 인정됩니다. 격리 수준을 표로만 외운 사람은 이 설명을 못 합니다. 덧붙여 SERIALIZABLE에서는 평범한 SELECT도 SELECT ... FOR SHARE로 바뀌어 공유 락을 잡기 때문에 읽기만 해도 쓰기를 막습니다.

06

함정 — Lost Update는 트랜잭션을 걸어도 막히지 않는다

"트랜잭션 걸면 동시성 문제가 해결된다"는 답변에 대한 반례입니다. 재고 10개에서 두 명이 동시에 1개씩 사는 상황을 재현합니다.

T1
SELECT stock → 10 UPDATE stock = 9
T2
SELECT stock → 10 UPDATE stock = 9
2 2 판매된 개수
vs
10 9 9 실제 재고 (10에서 얼마나 줄었나)

2개 팔았는데 1개만 줄었다 — 한 트랜잭션의 UPDATE가 덮어써져 사라졌습니다

01T1이 재고를 읽습니다. 10개.

02T2도 재고를 읽습니다. 역시 10개. MVCC는 이걸 막지 않습니다.

03T1이 애플리케이션에서 10 - 1 = 9를 계산해 SET stock = 9로 씁니다.

04T2도 같은 계산으로 SET stock = 9를 씁니다. T1의 결과를 덮어씁니다.

052개 판매인데 재고는 1개만 줄었습니다. 이게 Lost Update입니다.

해결책 3가지 — 면접에서 자주 파고듭니다

-- (1) 원자적 UPDATE — 가장 간단하고 가장 빠르다. 읽기 없이 DB에서 계산한다
UPDATE products SET stock = stock - 1 WHERE id = 1 AND stock >= 1;
-- 영향받은 행 수가 0이면 재고 부족으로 처리

-- (2) 비관적 락 — 읽고 나서 판단할 로직이 복잡할 때. 충돌이 잦으면 이쪽
SELECT stock FROM products WHERE id = 1 FOR UPDATE;

-- (3) 낙관적 락 — 버전 컬럼으로 충돌 감지, 충돌 시 재시도. 충돌이 드물면 이쪽
UPDATE products SET stock = 9, version = version + 1
 WHERE id = 1 AND version = 3;
💡

선택 기준은 충돌 빈도입니다. 잦으면 비관적 락, 드물면 낙관적 락.

그리고 "애플리케이션에서 읽어서 계산한 뒤 쓴다"는 패턴 자체가 위험 신호입니다. DB 안에서 계산할 수 있으면 (1)번이 항상 정답에 가깝습니다.

07

데드락 — 서로가 가진 락을 기다려 영원히 진행되지 않는 상태

T1은 A를 잡고 B를 기다리고, T2는 B를 잡고 A를 기다립니다. 원이 닫히는 순간 아무도 못 움직입니다.

T1계좌 A → B 이체
T2계좌 B → A 이체
🔒 A 락 획득 ⏳ B 락 대기…
🔒 B 락 획득 ⏳ A 락 대기…
↻ 순환 대기 — 아무도 앞으로 못 간다
InnoDBinnodb_deadlock_detect = ON
T2 강제 롤백에러 1213 ER_LOCK_DEADLOCK
T1 진행정상 커밋

롤백 대상은 보통 변경량이 적은 쪽(undo log가 작은 쪽)입니다.

01T1이 A 계좌 행의 락을 잡습니다.

02거의 동시에 T2가 B 계좌 행의 락을 잡습니다. 여기까지는 문제없습니다.

03T1은 B를, T2는 A를 원합니다. 둘 다 상대가 쥔 락을 기다립니다.

04대기 그래프에 사이클이 생겼습니다. 이게 데드락입니다.

05InnoDB가 감지해서 한쪽을 롤백합니다. 클라이언트는 1213 에러를 받습니다.

에러 코드 구분

1213
데드락 감지 → 자동 롤백. 재시도하면 대체로 성공
1205
락 대기 타임아웃(innodb_lock_wait_timeout 기본 50초)
SHOW ENGINE INNODB STATUS;
-- LATEST DETECTED DEADLOCK 섹션에서 원인 분석

예방책 (효과 순서)

  1. 락 획득 순서를 통일한다. 항상 작은 ID부터. 가장 효과적
  2. 트랜잭션을 짧게 유지한다. 락 보유 시간 = 충돌 확률
  3. 인덱스를 제대로 걸어 락 범위를 좁힌다 (다음 장면)
  4. 완전히 없앨 수 없다고 가정하고 재시도를 넣는다
// Go — 지수 백오프 + 지터로 재시도. 같은 타이밍에 다시 부딪히는 걸 피한다
const mysqlErrDeadlock = 1213

func isDeadlock(err error) bool {
   var me *mysql.MySQLError
   return errors.As(err, &me) && me.Number == mysqlErrDeadlock
}

for attempt := 1; attempt <= maxAttempts; attempt++ {
   err = Transfer(ctx, db, from, to, amount)
   if err == nil || !isDeadlock(err) { return err }
   backoff := time.Duration(1<<attempt)*10*time.Millisecond +
      time.Duration(rand.Intn(20))*time.Millisecond
   select {
   case <-ctx.Done(): return ctx.Err()
   case <-time.After(backoff):
   }
}
💡

데드락은 "없애는" 게 아니라 "줄이고 대비하는" 것입니다.

면접에서 예방책만 나열하고 재시도를 말하지 않으면 반쪽입니다. 1213은 정상적으로 발생할 수 있는 에러이고, 재시도 로직은 선택이 아니라 기본입니다.

08

InnoDB의 락은 행이 아니라 인덱스 레코드에 걸린다

그래서 인덱스 설계가 곧 락 범위 설계입니다. "인덱스가 왜 중요한가"에 성능 말고 하나 더 답할 수 있는 카드입니다.

UPDATE orders SET status = 'DONE' WHERE status = 'PENDING'; — 대상은 100행 중 3행

status에 인덱스가 없다

풀 스캔하면서 스캔한 모든 행에 락을 겁니다. 사실상 테이블 전체가 잠깁니다.

잠긴 행 0 잠긴 행 40 잠긴 행 100

status에 인덱스가 있다

인덱스로 대상 3행만 찾아가 그 레코드에만 락을 겁니다. 나머지 97행은 자유롭게 읽고 씁니다.

잠긴 행 0 잠긴 행 3

레코드 락 갭 락 — 레코드 사이 빈 구간에 INSERT 차단 넥스트키 락 — 레코드 락 + 앞 갭 락 (RR의 기본 동작) 인텐션 락 IS/IX — 테이블 수준, DDL 충돌 감지용

01같은 UPDATE 문을 인덱스 유무만 바꿔서 실행합니다.

02왼쪽은 순차적으로 훑으며 지나간 행마다 락을 겁니다. 오른쪽은 3행만 찾아갑니다.

03왼쪽은 끝까지 스캔해 100행 전체가 잠깁니다. 다른 트랜잭션은 전부 대기합니다.

04락의 범위는 이렇게 나뉩니다. 팬텀을 막는 갭 락도 인덱스 위에 걸립니다.

💡

인덱스는 성능 도구이면서 동시에 동시성 도구입니다.

"락 대기가 늘었다 / 데드락이 늘었다"의 원인이 인덱스 부재인 경우가 아주 많습니다. 인덱스 편과 이어지는 지점이고, 두 주제를 연결해서 말하면 확실히 차별화됩니다.

차별점

실무에서 주의한 점 — 여기가 신입/주니어를 가른다

ACID와 격리 수준은 누구나 외워옵니다. 이 세 가지는 겪어본 사람만 말합니다.

❌ 안티패턴

tx 시작
  → DB 저장
  → PG 결제 승인 API 호출 (3초)
  → DB 저장
  → 커밋
  • DB 커넥션을 외부 응답 시간만큼 점유 → 커넥션 풀 고갈
  • 락을 그 시간만큼 붙잡음 → 데드락·락 대기 급증
  • 외부 호출은 롤백되지 않는다 → DB는 롤백됐는데 결제는 승인됨

✅ 트랜잭션 경계를 쪼갠다

tx1: pending 레코드 저장 후 커밋
  → PG API 호출 (트랜잭션 밖)
tx2: 결과로 상태 업데이트 후 커밋
  → 미확정 건은 배치로 PG에 조회
     (reconciliation)

핵심은 외부 호출 전에 의도를 먼저 커밋하는 것입니다. 어느 시점에 죽어도 추적 가능한 흔적이 남습니다. 멱등성 편에서 이어집니다.

  • 트랜잭션 범위를 최소화한다. 조회, 파일 업로드, 이미지 리사이즈, 로깅은 트랜잭션 밖으로. "핸들러 전체를 트랜잭션으로 감싸는" 구조는 나중에 반드시 문제가 됩니다.
  • 커넥션 풀 크기와 트랜잭션 길이는 같은 문제다. SetMaxOpenConns를 올리기 전에 트랜잭션 길이를 먼저 봅니다.
  • 읽기 전용은 명시한다. sql.TxOptions{ReadOnly: true}를 주면 InnoDB가 트랜잭션 ID 할당을 생략해 약간 더 빠릅니다.
// Go 기본 패턴 — 커밋 성공 후의 Rollback은 sql.ErrTxDone을 반환하고 아무 일도 안 한다.
// 그래서 defer로 걸어두는 게 안전하다 (panic이나 early return에서도 정리됨).
func withTx(ctx context.Context, db *sql.DB, fn func(*sql.Tx) error) error {
   tx, err := db.BeginTx(ctx, nil)
   if err != nil {
      return fmt.Errorf("begin tx: %w", err)
   }
   defer func() { _ = tx.Rollback() }()

   if err := fn(tx); err != nil {
      return err
   }
   return tx.Commit()
}
정리

이 8장면을 한 문단으로

트랜잭션은 여러 작업을 하나의 논리적 단위로 묶는 개념입니다. 성질은 ACID이고, InnoDB는 원자성을 undo log로, 지속성을 redo log(WAL)로, 격리성을 MVCC와 락으로 구현합니다. 격리 수준은 세 가지 이상 현상을 얼마나 막는지로 나뉘고, MySQL 기본은 REPEATABLE READ입니다. READ COMMITTED와의 차이는 ReadView 생성 시점 한 줄입니다. 단, 격리 수준이 모든 걸 해결하지는 않습니다. Lost Update는 원자적 UPDATE나 락으로 직접 막아야 합니다. 락은 행이 아니라 인덱스 레코드에 걸리므로 인덱스 설계가 락 범위 설계이고, 데드락은 순서 통일·짧은 트랜잭션·재시도로 다룹니다. 실무에서는 트랜잭션 안에서 외부 API를 호출하지 않는 것이 가장 중요했습니다.

자주 하는 실수

  • ACID 네 글자만 나열하고 끝낸다 → 각각을 InnoDB가 어떻게 구현하는지까지 가야 합니다
  • 격리 수준 이름만 외우고 어떤 이상 현상을 막는지 연결하지 못한다
  • MySQL 기본값을 READ COMMITTED로 답한다 (그건 PostgreSQL/Oracle)
  • "트랜잭션 걸면 동시성 문제가 해결된다"고 답한다 → Lost Update 반례가 있습니다
  • 겪은 사례가 없다 → 데드락이든 락 대기든 커넥션 풀 고갈이든 본인 경험 하나는 반드시 준비
