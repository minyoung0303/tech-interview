01

Scale-up은 키우고, Scale-out은 늘린다

Scale-up은 코드를 안 고쳐도 되니 간단합니다. 대신 물리적 상한이 있고, 보통 재시작이 필요하고, 단일 장애점이 그대로 남습니다. Scale-out은 그 세 가지를 해결하지만 로드 밸런서와 stateless를 요구합니다.

한 대 죽어도 서비스는 살아 있다 전제: stateless

01서버 1대로 시작합니다. 트래픽이 늘기 시작했습니다.

02가장 쉬운 대응은 사양을 올리는 것입니다. 코드를 한 줄도 안 고쳐도 됩니다. 대신 인스턴스 타입을 바꾸려면 재시작이 필요합니다.

03더 올립니다. 그런데 비용은 사양보다 빠르게 오릅니다. 고사양일수록 단가가 비쌉니다.

04결국 물리적 상한에 닿습니다. 그리고 무엇보다 — 이 한 대가 죽으면 전면 장애입니다. 단일 장애점은 해결되지 않았습니다.

05그래서 대수를 늘립니다. 앞에 로드 밸런서가 필요하고, 어느 서버로 가도 같은 결과가 나오려면 서버가 상태를 갖고 있지 않아야 합니다. 다음 장면입니다.

💡

"일단 Scale-up으로 버티는 것"은 나쁜 선택이 아닙니다.

Scale-out은 분산 트랜잭션, 캐시 일관성, 디버깅 난이도 같은 영구적인 복잡도를 추가합니다. 엔지니어 시간이 서버 비용보다 비싼 경우가 많습니다. 그리고 실무의 정답은 대체로 "애플리케이션은 Scale-out, DB는 먼저 Scale-up"입니다. 쓰기 확장은 샤딩까지 가야 해서 비용이 완전히 다릅니다.

02

Scale-out에서 진짜 어려운 건 상태를 밖으로 빼는 일

서버를 늘리는 건 버튼 하나입니다. 문제는 그 서버가 갖고 있던 것입니다. 세션이 파드 메모리에 있으면 늘리는 순간 로그인이 풀립니다.

01로그인 요청이 파드A로 갑니다.

02파드A가 자기 메모리에 세션을 저장합니다. 파드가 1대면 여기서 끝, 아무 문제 없습니다.

03파드를 3대로 늘렸습니다. 다음 요청은 로드 밸런서가 파드B로 보냅니다.

04파드B에는 그 세션이 없습니다. 401, 로그아웃됩니다. Scale-out이 깨진 순간입니다.

05해결은 세션 저장소를 애플리케이션 밖으로 빼는 것입니다. Redis / ElastiCache.

06이제 어느 파드로 가도 같은 결과입니다. 애플리케이션이 stateless해졌고, 그때 비로소 마음껏 늘릴 수 있습니다.

❌ 임시 처방 — Sticky Session

쿠키나 소스 IP 해시로 같은 사용자를 항상 같은 서버로 보냅니다. 동작은 합니다. 그런데—

  • 배포로 파드가 교체될 때마다 세션이 날아간다
  • 오토 스케일링으로 파드가 줄어들 때도 마찬가지

03

L4는 봉투만 보고, L7은 편지를 열어 읽는다

L4는 전송 계층에서 IP와 포트만 봅니다. L7은 애플리케이션 계층에서 메서드·경로·헤더·쿠키까지 읽습니다. 여기서 모든 차이가 파생됩니다.

L4 (NLB) 가 보는 것

dst 10.0.1.20 : 443 proto TCP GET /api/orders HTTP/1.1 Host: shop.example.com Cookie: sid=abc…

HTTP를 파싱하지 않으므로 경로 기반 라우팅이 원리적으로 불가능합니다. 대신 가볍고 빠르고, TCP면 무엇이든 흘려보냅니다.

L7 (ALB / Nginx) 가 보는 것

dst 10.0.1.20 : 443 proto TCP GET /api/orders HTTP/1.1 Host: shop.example.com Cookie: sid=abc…

내용을 읽으려면 TLS를 복호화해야 합니다. 그래서 L7에서 TLS 종료가 자연스럽게 따라옵니다.

/api/* /admin/* /static/*

01같은 요청이 들어옵니다. L4는 목적지 IP와 포트, 프로토콜까지만 봅니다. 그 아래 HTTP는 그냥 바이트입니다.

02L7은 HTTP를 해석합니다. 메서드, 경로, Host, 쿠키가 전부 보입니다. 보려면 TLS를 복호화해야 합니다.

03그래서 경로별로 다른 서버로 보내는 일이 가능해집니다. MSA의 진입점이 여기입니다.

04L7의 핵심 구조는 연결이 두 개로 끊긴다는 것입니다. 그래서 TLS 종료가 되고, 클라이언트 IP가 사라져 X-Forwarded-For가 필요하고, 타임아웃이 두 겹이 되고, 느린 클라이언트를 흡수할 수 있습니다.

05거꾸로 L4는 거의 그대로 흘려보내므로 그런 걸 못 하지만 훨씬 빠르고, 고정 IP를 주고, HTTP가 아닌 프로토콜도 다룹니다.

💡

선택 기준은 "L7이 더 좋다"가 아니라 목적입니다.

NLB: 고정 IP가 필요할 때(상대방이 IP 화이트리스트를 요구), 초저지연, HTTP가 아닌 프로토콜, 클라이언트 IP를 그대로 받고 싶을 때.
ALB: 경로·호스트 라우팅, TLS 종료, WAF 연동, 인증 연동.

둘 다 쓰는 구성도 흔합니다. NLB → Nginx Ingress → 서비스. 고정 IP와 L4 성능은 NLB에서, 경로 라우팅은 뒤의 Nginx에서 얻습니다. 이걸 말하면 구조를 그려본 사람으로 읽힙니다. 자세한 프록시 이야기는 프록시 편에 있습니다.

04

Web과 WAS를 나누는 이유 — 정적 요청을 앞에서 흡수한다

WAS의 워커 수는 유한하고 비쌉니다. 이미지 요청이 WAS까지 올라가면 비즈니스 로직용 워커가 파일 전송에 묶입니다.

❌ 앱 서버가 전부 처리

GET /logo.svg GET /app.js POST /api/orders
WAS워커 4개

워커 4개 중 3개가 정적 파일 전송에 묶여 있습니다. 주문 요청은 큐에서 기다립니다.

■ 정적 전송   ■ 로직 처리   □ 유휴

✅ Web이 앞에서 흡수

GET /logo.svg GET /app.js POST /api/orders
WebNginx / CDN
WAS워커 4개

정적 요청은 Web에서 끝납니다. WAS는 로직만 처리하니 같은 사양으로 훨씬 많은 주문을 받습니다.

정적 요청은 여기까지 오지 않는다

01정적 자원 오프로드 — WAS 워커를 비즈니스 로직에만 쓴다
02보안 경계 — WAS를 Private Subnet에 두고 Web/LB만 노출한다 (VPC 편)
03여러 WAS를 하나로 묶는다 — 로드 밸런싱, 헬스 체크, 무중단 배포의 전제
04공통 관심사 분리 — TLS, 압축, 캐시 헤더, 요청 크기 제한, Rate Limit, WAF
05느린 클라이언트 흡수 — 요청을 다 받은 뒤 한 번에 넘겨서 워커를 붙잡히지 않게 한다
06장애 격리 — WAS가 전부 죽어도 502 대신 점검 페이지를 보여줄 수 있다

01정적 파일 요청과 API 요청이 섞여 들어옵니다. 실제 트래픽에서 정적 요청이 훨씬 많습니다.

02앞에 Web 계층을 둡니다. Nginx, 또는 요즘이면 CloudFront + S3입니다.

03동적 요청만 WAS로 넘어갑니다. 같은 사양으로 처리량이 몇 배 올라갑니다.

04그런데 실무에서 더 큰 이유는 성능이 아니라 구조입니다. 여섯 가지를 봅니다.

052번(보안 경계)과 3번(로드 밸런싱)이 실무에서 가장 큰 이유입니다. "정적/동적"만 말하면 절반입니다.

💡

"그럼 Nginx 없이 앱만 띄우면 안 되나요?" — 이 꼬리질문이 반드시 옵니다.

됩니다. 요즘은 정적 파일은 CDN/S3로 가고, TLS 종료와 L7 라우팅은 ALB가 하고, 컨테이너 안에는 앱 프로세스만 두는 게 원칙입니다(1 컨테이너 1 프로세스). 즉 역할 분리라는 개념은 그대로인데 Web 계층의 구현체가 Nginx에서 CloudFront·ALB·Ingress Controller로 옮겨간 것입니다. 

[예전] Nginx (EC2)  →  Tomcat
[요즘] CloudFront → ALB → (Nginx Ingress) → 앱 컨테이너

이렇게 답하면 개념과 현실을 둘 다 아는 것으로 읽힙니다.

05

파드를 늘렸는데 더 느려졌다 — 병목은 아래로 내려간다

앱은 무한히 늘릴 수 있어도 DB는 한 대입니다. 파드 수 × 커넥션 풀 크기가 DB의 max_connections를 넘는 순간 전면 장애가 납니다.

ALB

대응

풀 크기
파드 수를 고려해 파드당 풀을 줄인다. 풀은 크다고 좋은 게 아니다
RDS Proxy
커넥션을 풀링·다중화해서 DB 쪽 커넥션 수를 줄인다

같이 확인할 병목

  • 락 경합 — 동시성이 올라가면 같은 행을 다투다 데드락이 늘어난다 (트랜잭션 편)
  • 인덱스 부재 — 풀 스캔은 락 범위까지 넓힌다 (인덱스 편)
  • 외부 API rate limit — 내 서버만 늘어나고 상대는 그대로다
  • Redis 단일 노드 — 세션을 밖으로 뺐다면 여기가 새 병목이 될 수 있다

01파드 1개, 커넥션 풀 20개. DB 커넥션 20개를 씁니다. 여유롭습니다.

02파드를 3개로 늘립니다. 커넥션은 3 × 20 = 60개. 아직 괜찮습니다.

03트래픽 스파이크에 오토 스케일링이 파드를 10개까지 늘립니다. 10 × 20 = 200개. 한계 151을 넘었습니다.

04Too many connections. 새로 뜬 파드뿐 아니라 기존 파드도 커넥션을 못 얻습니다. Scale-out이 장애의 원인이 된 순간입니다.

05대응은 풀 크기 조정, RDS Proxy, 읽기 분리, 캐시입니다. 그리고 Scale-out의 병목은 결국 DB로 내려간다는 인식이 남습니다.

💡

"확장" 질문에 순서를 말할 수 있으면 판단력으로 읽힙니다.

Scale-out보다 먼저 해야 할 것이 있습니다 — ① 인덱스·쿼리 튜닝 → ② N+1 제거·커넥션 풀 조정 → ③ 캐시 → ④ Scale-up → ⑤ Scale-out → ⑥ 아키텍처 변경. 대부분 ①에서 끝나고, 그게 가장 쌉니다. "무조건 서버를 늘리자"고 답하는 지원자와 갈리는 지점입니다.

06

세션 vs JWT — 갈리는 건 상태를 어디에 두는가

"세션은 Scale-out에 불리하다"는 건 정확하지 않습니다. 불리한 건 세션을 서버 메모리에 두는 것이고, Redis로 빼면 세션도 충분히 확장됩니다. JWT는 저장소 조회를 없애는 대신 즉시 무효화를 잃는 교환입니다.

① 세션 · 서버 메모리

요청 + 쿠키 sid→ 파드B 메모리 조회→ 세션 없음→ 401 Scale-out 불가 · sticky session 필요

② 세션 · Redis

요청 + 쿠키 sid→ 어느 파드든→ Redis 조회→ 인증 OK 앱은 stateless · 즉시 무효화 가능 요청마다 네트워크 홉 1회

③ JWT

요청 + Bearer 토큰→ 어느 파드든→ 서명 검증만→ 인증 OK 저장소 조회 0회 · 완전 stateless 발급한 토큰을 즉시 무효화할 수 없다

01세션 ID를 쿠키로 보내고 서버가 저장소에서 찾는 방식이 기본입니다. 문제는 그 저장소가 어디냐입니다.

02파드 메모리에 두면 다른 파드로 갔을 때 세션이 없습니다. sticky session으로 버티게 되고, 그러면 분산과 배포가 함께 망가집니다.

03Redis로 빼면 어느 파드로 가도 동일합니다. 앱은 stateless가 되고 Scale-out에 문제가 없습니다. 대가는 요청마다 네트워크 홉 1회와 Redis 의존성입니다.

04JWT는 토큰 안에 정보와 서명이 있어서 저장소를 아예 안 봅니다. 서비스가 여러 개일 때 각자 공개키로 독립 검증할 수 있다는 게 큰 장점입니다.

05대가는 즉시 무효화 불가입니다. 그리고 Payload는 암호화가 아니라 Base64 인코딩입니다. 민감정보를 넣으면 안 됩니다.

"JWT는 암호화되어 있다"는 치명적인 오답입니다.

JWT는 서명입니다. 서명은 "내용이 바뀌지 않았음"만 보장합니다. Payload는 Base64URL 인코딩이라 누구나 디코딩해서 읽습니다. 비밀번호, 주민번호, 민감 개인정보를 넣으면 안 됩니다. 이 한 줄을 말하면 보안 감각이 있는 것으로 읽힙니다.

07

JWT의 아이러니 — 무효화하려면 stateless를 포기해야 한다

토큰이 탈취됐습니다. 강제 로그아웃을 해야 합니다. 그런데 서버는 그 토큰을 갖고 있지 않습니다.

토큰 발급→ 탈취 발생→ 강제 로그아웃 시도→ 서버에 지울 게 없다→ 블랙리스트 도입

세션이라면

01저장소에서 세션을 지운다
02다음 요청부터 즉시 401
✓끝. 이게 서버 상태의 장점이다

JWT라면

01서버는 발급한 토큰 목록을 모른다
02exp까지 계속 유효하다
03Redis 블랙리스트를 둔다 → 동작한다
!그런데 매 요청마다 Redis를 조회하게 된다 — stateless 장점이 사라진다
// 실무 표준: 하이브리드 — 상태를 "어느 경로에 둘지" 고른다
Access  Token : JWT,      만료 5~15분,  저장소 조회 없이 검증   // 빠른 경로는 stateless
Refresh Token : 불투명 토큰, 만료 2주,    DB/Redis에 저장       // 느린 경로에만 상태

// Refresh 저장 위치와 규칙
Set-Cookie: refresh=…; HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh

// Rotation  : 쓸 때마다 새로 발급하고 이전 것을 폐기
// 재사용 감지: 폐기된 refresh가 다시 오면 탈취로 보고 계열 전체를 폐기

01로그인 시 JWT를 발급했습니다. 서버는 이 토큰을 저장하지 않습니다. 그게 설계 의도입니다.

02토큰이 탈취됐습니다. 또는 관리자가 사용자 권한을 박탈했습니다.

03세션이라면 저장소에서 지우면 끝입니다. JWT는 지울 대상이 없습니다.

04토큰은 exp까지 계속 유효합니다. 권한을 박탈해도 토큰 안의 role은 발급 시점 값이라 만료까지 예전 권한으로 통과합니다.

05블랙리스트를 두면 해결되지만 매 요청마다 조회가 생겨 stateless가 깨집니다. 그래서 현실적인 답은 access는 짧게, refresh는 서버에 저장하는 하이브리드입니다.

💡

결국 상태는 어딘가에 있어야 합니다. 선택은 "어느 요청 경로에 둘지"입니다.

모든 요청이 지나는 검증 경로에서는 상태를 없애고(JWT), 드물게 지나는 갱신 경로에만 상태를 둡니다(Refresh). 이게 하이브리드의 논리이고, 이 문장을 말할 수 있으면 이 질문은 통과입니다.

판단 기준: 강제 로그아웃·권한 즉시 반영이 중요하면 Redis 세션 또는 불투명 토큰, 서비스가 여러 개이고 각자 독립 검증해야 하면 JWT. 금융·결제처럼 즉시 차단이 필수인 도메인은 서버 상태를 포기하지 않습니다.

JWT 검증에서 놓치면 안 되는 것

alg: none 공격 — 알고리즘은 서버가 지정한 것으로 고정하고 토큰 헤더를 믿지 않습니다. HS256/RS256 confusion, exp·iss·aud 검증 누락, 서명 검증 없이 디코드만 하는 함수를 인증에 쓰는 실수도 함께 봅니다. 저장 위치는 access는 메모리, refresh는 HttpOnly 쿠키가 정석입니다 (localStorage는 XSS에 노출됩니다).

순서

"트래픽이 늘면 어떻게 하시겠어요?" — 답은 순서다

이 질문에 "서버를 늘립니다"라고 답하면 절반입니다. 측정 → 싼 것부터가 실무 순서입니다.

01병목을 측정한다 — slow query log, APM, 골든 시그널 4개(지연·트래픽·에러·포화도)
02인덱스 · 쿼리 튜닝 — 대부분 여기서 끝난다. 가장 싸고 효과가 크다 (인덱스 편)
03N+1 제거, 커넥션 풀 조정
04캐시 — CDN, Redis, 애플리케이션 캐시. 읽기 부하는 Replica보다 캐시가 먼저인 경우가 많다
05Scale-up — 시간을 버는 카드. 나쁜 선택이 아니다
06Scale-out — LB + stateless. 상태를 밖으로 빼는 작업이 실제 비용이다
07읽기 분리 (Read Replica) — 복제 지연을 다룰 준비가 필요하다 (DB 확장 편)
08비동기화 · CQRS · 검색엔진 분리 — SQS로 밀어내기, 무거운 조회는 별도 저장소로
09샤딩 — 마지막. 되돌리기가 가장 어렵다
💡

한 문단으로 외워두면 인프라 파트 전체가 하나의 답변이 됩니다.

"트래픽이 늘면 먼저 병목을 측정하고, 인덱스와 캐시로 해결되는지 봅니다. 안 되면 Scale-up으로 시간을 벌고 그다음 Scale-out을 합니다. Scale-out을 하려면 앞에 로드 밸런서가 필요하고 애플리케이션이 stateless여야 합니다. 그래서 세션을 Redis로 빼거나 JWT를 쓰고, 파일은 S3로, 로그는 stdout으로 보냅니다. 서버를 똑같이 여러 개 찍어내려면 컨테이너가 필요하고, 그것들을 VPC의 Private Subnet에 두고 앞단에만 ALB를 노출합니다. 교체는 롤링/블루그린/카나리로 하는데 헬스 체크와 graceful shutdown이 없으면 무중단이 아닙니다. 앱을 늘리면 병목은 결국 DB로 내려갑니다."

정리

이 7장면을 한 문단으로

Scale-up은 키우고 Scale-out은 늘립니다. Scale-up은 쉽지만 상한·재시작·단일 장애점이 남고, Scale-out은 그걸 해결하는 대신 로드 밸런서와 stateless를 요구합니다. 그래서 세션은 Redis로, 파일은 S3로, 로그는 stdout으로 빼야 합니다. 앞에 서는 로드 밸런서는 L4(IP·포트, NLB)와 L7(HTTP 내용, ALB)로 갈리고, L7은 연결을 두 개로 끊기 때문에 TLS 종료·XFF·두 겹 타임아웃이 따라옵니다. 정적 요청은 Web 계층이 앞에서 흡수하고 WAS는 로직만 처리하며, 그 Web 계층의 구현체는 이제 CloudFront·ALB·Ingress입니다. 인증은 서버 메모리 세션(확장 불가) → Redis 세션(정석) → JWT(조회 제거, 무효화 상실) 순으로 트레이드오프가 바뀌고, 실무 답은 짧은 access + 저장된 refresh의 하이브리드입니다. 그리고 앱을 늘려도 병목은 DB로 내려갑니다.

자주 하는 실수

  • "Scale-up은 한계가 있으니 Scale-out이 좋다"로 끝낸다 → 트레이드오프와 stateless 전제를 말해야 한다
  • DB를 앱과 똑같이 취급한다 → 쓰기 확장은 완전히 다른 문제다
  • L4/L7만 외우고 실무 제품(ALB/NLB)과 연결하지 못한다
  • 헬스 체크를 언급하지 않는다 → 헬스 체크 없는 로드 밸런싱은 무중단이 아니다
  • Web/WAS를 "정적/동적"으로만 설명한다 → 보안 경계와 로드 밸런싱이 실무의 더 큰 이유다
  • "세션은 확장에 불리하고 JWT가 좋다"고 단정한다 → Redis 세션이 정석이다. 이 교정이 가장 큰 가산점
  • "JWT는 암호화되어 있다"고 말한다 → 서명이다. 치명적인 오답
  • JWT의 즉시 무효화 문제를 모른다 → 실제로 써본 적 없다는 신호로 읽힌다
