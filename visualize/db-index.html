01

풀 스캔 O(N) vs 인덱스 탐색 O(log N)

100만 행 테이블에서 한 행을 찾습니다. 왼쪽은 처음부터 다 읽고, 오른쪽은 정렬된 트리를 타고 내려갑니다.

인덱스 없음 — Full Table Scan

0 340,000 720,000 1,000,000 비교 횟수 · type = ALL

인덱스 있음 — B+Tree 탐색

root
branch
leaf → 행
0 7 14 20 비교 횟수 · type = ref

01같은 조건으로 같은 한 행을 찾습니다. 시작 상태입니다.

02왼쪽은 한 행씩 비교하며 전진합니다. 오른쪽은 루트 노드에서 방향만 정합니다.

03왼쪽은 아직 절반 지점. 오른쪽은 벌써 브랜치 → 리프로 내려갔습니다.

04100만 번 vs 20번. 트리 높이가 보통 3~4단계라서 이렇게 됩니다.

💡

단, 인덱스가 항상 이득은 아닙니다.

조회 결과가 테이블의 상당 부분(대략 20~30% 이상)이면 인덱스를 타고 랜덤 I/O를 반복하는 것보다 순차적으로 다 읽는 게 빠릅니다. 옵티마이저가 일부러 인덱스를 무시하고 풀 스캔을 고르는 건 버그가 아니라 정상 동작입니다.

이 두 가지 특징이 인덱스의 성질을 전부 설명합니다. WHERE id = 55를 찾아 내려간 뒤, 범위 조회로 옆으로 훑어봅니다.

브랜치는 길잡이일 뿐 — 데이터가 없어서 가볍다 WHERE id = 55 → 30~70 구간으로 브랜치 [40|50|60] → 50 이상 구간으로 리프 도달. 여기서 3홉 끝 BETWEEN 50 AND 90 → 리프를 옆으로 쭉

01데이터(또는 데이터 포인터)는 리프 노드에만 있습니다. 그래서 브랜치가 가볍고 트리 높이가 낮게 유지됩니다.

02루트에서 55가 속한 구간을 고릅니다. 비교 몇 번으로 후보가 3분의 1로 줄어듭니다.

03브랜치에서 한 번 더 좁힙니다.

04리프에 도달했습니다. 100만 행이어도 보통 3~4홉입니다.

05리프끼리 연결돼 있으니 범위 조회는 하나 찾고 옆으로 훑으면 끝입니다.

💡

"왜 해시 인덱스가 아니라 B+Tree인가요?"는 거의 항상 나옵니다.

해시는 등호 비교만 O(1)로 처리하고 범위 조회와 정렬을 전혀 못 합니다. 실무 쿼리 대부분이 BETWEEN, >, ORDER BY를 포함하므로 범용 인덱스는 B+Tree여야 합니다. InnoDB에 Adaptive Hash Index가 있지만 옵티마이저가 자동으로 쓰는 것이고 사용자가 만들 수는 없습니다.

03

세컨더리 인덱스로 조회하면 두 번 탐색한다

InnoDB에서 테이블 데이터 자체가 PK 순서로 정렬 저장됩니다(클러스터드 인덱스). 세컨더리 인덱스 리프에는 행이 아니라 PK 값만 들어 있습니다.

SELECT * FROM users WHERE email = 'kim@ex.com';

세컨더리 인덱스idx_email (email)
리프: email + PK
PK = 41얻은 건 행이 아니라 PK
클러스터드 인덱스= PK. 리프가 곧 행 전체
41 → 모든 컬럼
↑ 이 2단계가 랜덤 I/O — 흔히 북마크 룩업이라 부른다 행 전체 획득 완료

PK가 크면?

id CHAR(36) PRIMARY KEY
-- UUID v4. 36바이트가
-- 모든 세컨더리 인덱스에 복사된다

세컨더리 인덱스 전부가 PK 값을 품고 있습니다. 게다가 랜덤한 PK로 INSERT하면 페이지 중간에 끼워넣게 되어 페이지 분할(page split)이 자주 일어납니다.

그래서 PK는 짧고 단조 증가해야 한다

id BIGINT AUTO_INCREMENT
   PRIMARY KEY
-- 8바이트. 항상 맨 뒤에 붙어
-- 페이지 분할이 거의 없다

UUID를 꼭 써야 하면 시간 순서가 보장되는 UUID v7이나 ULID를 쓰고, 저장은 BINARY(16)으로 하는 게 정석입니다.

01email로 세컨더리 인덱스를 탐색합니다.

02얻은 것은 행이 아니라 PK 값입니다. 여기서 끝나지 않습니다.

03그 PK로 클러스터드 인덱스를 다시 탐색합니다. 이게 랜덤 I/O입니다.

04드디어 행 전체를 읽습니다. SELECT *는 이 2단계를 항상 거칩니다.

05여기서 나오는 실전 결론 두 개 — PK는 짧아야 하고 단조 증가해야 합니다.

💡

"PK를 UUID로 하면 어떤 문제가 있나요?"에 두 가지를 다 말해야 합니다.

① 모든 세컨더리 인덱스가 비대해진다 ② 랜덤 삽입으로 페이지 분할과 단편화가 생긴다. 하나만 말하면 절반입니다. 그리고 UUID v7 / ULID / BINARY(16)까지 얹으면 확실히 눈에 띕니다.

04

커버링 인덱스 — 방금 그 2단계가 사라진다

쿼리에 필요한 모든 컬럼이 인덱스 안에 있으면 클러스터드 인덱스를 다시 갈 이유가 없습니다.

커버링 아님

CREATE INDEX idx_status
    ON orders (status);

SELECT customer_name -- 인덱스에 없다
  FROM orders WHERE status = 'PAID';
① 인덱스 탐색 ② 클러스터드 재탐색

Extra: Using where

커버링

CREATE INDEX idx_s_c_a
    ON orders (status, created_at, amount);

SELECT amount -- 전부 인덱스 안에 있다
  FROM orders
 WHERE status = 'PAID'
   AND created_at >= '2026-01-01';
① 인덱스 탐색 ②가 없다 — 여기서 끝

Extra: Using index ← 커버링의 증거

01같은 테이블, 비슷한 쿼리인데 필요한 컬럼이 인덱스에 있는지만 다릅니다.

02왼쪽은 행을 읽으러 클러스터드로 한 번 더 갑니다. 오른쪽은 인덱스만 읽고 끝냅니다.

03확인 방법은 EXPLAIN의 Extra: Using index 한 줄입니다.

💡

세컨더리 인덱스 리프에는 PK가 항상 들어 있으므로 PK 컬럼은 자동으로 커버됩니다.

CREATE INDEX idx_status ON orders(status) 상태에서 SELECT id FROM orders WHERE status='PAID'는 이미 커버링입니다. 이 사실이 다음 장면의 페이지네이션 최적화의 근거가 됩니다.

05

복합 인덱스는 왼쪽부터 연속으로만 쓸 수 있다

INDEX (a, b, c)는 "a로 정렬하고, a가 같으면 b로, b도 같으면 c로" 정렬한 하나의 목록입니다. 전화번호부를 성 → 이름 순으로 정렬한 것과 같습니다. 성을 모르면 이름만으로는 찾을 수 없습니다.

CREATE INDEX idx_a_b_c ON t (a, b, c); — 인덱스 리프의 실제 정렬 순서

a=1b=1c=5→ PK 101
a=1b=2c=3→ PK 240
a=1b=2c=9→ PK 118
a=1b=7c=1→ PK 305
a=2b=1c=4→ PK 072
a=2b=2c=8→ PK 411
a=3b=2c=2→ PK 199
a=3b=9c=6→ PK 288
정렬 순서: a → b → c WHERE a = 1 → 연속된 4건으로 좁혀진다 ✅ WHERE a = 1 AND b = 2 → 연속된 2건 ✅ WHERE b = 2 → 흩어져 있다 ❌ 인덱스를 못 쓴다 등호는 앞, 범위는 뒤

01복합 인덱스는 컬럼마다 따로 있는 게 아니라 하나의 정렬된 목록입니다.

02a = 1은 목록 앞부분의 연속 구간이라 바로 좁힐 수 있습니다.

03a = 1 AND b = 2도 그 안에서 다시 연속 구간입니다.

04b = 2만 주면 목록 전체에 흩어져 있습니다. 좁힐 방법이 없어 풀 스캔입니다.

05같은 이유로 범위 조건 이후의 컬럼도 탐색 범위를 좁히지 못합니다.

나쁜 순서 — 범위를 앞에

CREATE INDEX idx_bad
    ON orders (created_at, status);

SELECT * FROM orders
 WHERE created_at >= '2026-01-01'
   AND status = 'PAID';

created_at 범위 안의 모든 항목을 훑으면서 status를 하나하나 비교합니다.

좋은 순서 — 등호를 앞에

CREATE INDEX idx_good
    ON orders (status, created_at);

-- status로 딱 좁힌 뒤
-- 그 안에서 created_at 범위를 스캔
-- ORDER BY created_at DESC 도 공짜

인덱스가 이미 created_at 순으로 정렬돼 있으니 Using filesort가 사라집니다.

💡

컬럼 순서 결정의 1순위는 카디널리티가 아니라 쿼리 패턴입니다.

"카디널리티 높은 컬럼을 앞에"는 2순위입니다. 카디널리티가 높아도 그 컬럼이 WHERE에 안 들어오면 인덱스 자체를 못 탑니다. 순서는 ① 항상 등호로 들어오는 컬럼 → ② 그중 카디널리티 높은 것 → ③ 범위 조건 → ④ ORDER BY / GROUP BY.

그리고 INDEX(a)와 INDEX(a,b)가 같이 있으면 INDEX(a)는 중복이라 지워도 됩니다. 쓰기 비용만 늘립니다.

06

인덱스를 걸었는데도 안 타는 경우 — 제일 자주 묻습니다

공통 원인은 하나입니다. 인덱스가 유지하는 정렬 순서를 쓸 수 없게 만들었기 때문입니다.

① 인덱스 컬럼에 함수나 연산을 적용

-- X WHERE DATE(created_at) = '2026-01-01'
-- X WHERE price * 1.1 > 10000
-- X WHERE SUBSTRING(phone, 1, 3) = '010'

-- O 컬럼은 그대로 두고 반대쪽을 가공한다
WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'
WHERE price > 10000 / 1.1
WHERE phone LIKE '010%'

인덱스는 created_at의 순서를 알지만 DATE(created_at)의 순서는 모릅니다. MySQL 8.0.13+ 에서는 함수 기반 인덱스로 우회할 수 있습니다 — CREATE INDEX idx_d ON t ((DATE(created_at))). 괄호 두 겹이 문법 포인트입니다.

② 앞쪽 와일드카드 LIKE

LIKE 'kim%' → 시작점을 알 수 있다 ✅ LIKE '%kim' → 시작점이 없다 ❌ LIKE '%kim%' → ❌

전화번호부에서 "김"으로 시작하는 사람은 바로 펼칠 수 있지만, "~김"으로 끝나는 사람은 전부 봐야 합니다.

%kim이 꼭 필요하면 Full-Text 인덱스, 별도 검색 엔진(Elasticsearch), 또는 문자열을 뒤집어 저장한 컬럼에 인덱스를 거는 방법을 씁니다.

③ 타입 불일치 (암묵적 형변환)

-- phone은 VARCHAR인데
-- X WHERE phone = 01012345678   -- 컬럼을 숫자로 캐스팅해버린다
-- O WHERE phone = '01012345678'

Go에서 특히 잘 나는 실수입니다. int64 변수를 VARCHAR 컬럼에 바인딩하면 에러 없이 조용히 느려집니다.

조인할 때 양쪽 컬럼 타입이나 콜레이션이 다른 경우도 같은 이유로 인덱스를 못 탑니다. utf8mb4_general_ci와 utf8mb4_unicode_ci가 섞인 테이블 간 조인이 대표적입니다.

④ 선택도가 낮은 조건

status = 'PAID'인 행이 전체의 90%라면 인덱스를 타고 랜덤 I/O를 90만 번 하는 게 순차 스캔보다 느립니다. 옵티마이저가 일부러 풀 스캔을 고릅니다.

성별, is_deleted 같은 컬럼에 단독 인덱스를 거는 건 대체로 낭비입니다. 단, 복합 인덱스의 일부로 들어가는 건 다릅니다.

⑤ OR 조건 / 부정 조건

WHERE a = 1 OR b = 2
-- index merge로 처리될 수도 있지만 보장되지 않는다

-- UNION으로 쪼개는 게 확실할 때가 있다
SELECT ... WHERE a = 1
UNION
SELECT ... WHERE b = 2;

!=, <>, NOT IN, NOT LIKE는 "제외할 것"을 지정하므로 범위를 좁히지 못하는 경우가 많습니다.

01컬럼에 함수·연산을 적용하면 인덱스의 정렬을 쓸 수 없습니다. 가장 흔한 원인입니다.

02LIKE '%...'는 탐색 시작점이 없습니다.

03타입/콜레이션 불일치. 에러가 안 나서 발견이 늦습니다.

04선택도가 낮으면 옵티마이저가 일부러 인덱스를 버립니다.

05OR과 부정 조건은 인덱스로 범위를 좁히기 어렵습니다.

💡

다섯 가지를 외우는 것보다 원리 한 줄을 기억하는 게 낫습니다.

"인덱스의 정렬 순서로 탐색 범위를 좁힐 수 있는가." 좁힐 수 없으면 인덱스를 못 탑니다. 함수·앞쪽 와일드카드·형변환·부정 조건은 전부 이 한 가지 이유입니다.

07

트레이드오프 — INSERT 한 번에 트리 전부를 갱신한다

인덱스가 5개인 테이블에 한 행을 넣으면 클러스터드 1개 + 세컨더리 5개, 총 6개 트리가 수정됩니다.

INSERT 1건
1 2 6 갱신되는 트리 개수
PRIMARY
클러스터드

idx_status

  • 인덱스는 디스크 공간도 먹습니다. 큰 테이블에서 인덱스 총량이 데이터보다 커지는 경우도 흔합니다
  • UPDATE는 변경된 컬럼이 포함된 인덱스만 갱신합니다 → 자주 바뀌는 컬럼을 인덱스에 넣을 때 신중해야 합니다
  • 그래서 인덱스 설계는 항상 읽기 이득 vs 쓰기 비용의 저울질입니다

01PK(클러스터드) 트리는 무조건 갱신됩니다. 여기가 데이터 본체입니다.

02세컨더리 인덱스가 하나 있으면 트리 2개를 수정합니다.

03인덱스 5개면 트리 6개. INSERT/UPDATE/DELETE 모두 이 비용을 냅니다.

04공간과 UPDATE 특성까지 고려해야 인덱스 설계가 됩니다.

-- 실제로 안 쓰이는 인덱스 찾기 (performance_schema 활성 필요)
SELECT * FROM sys.schema_unused_indexes;

-- 중복 인덱스 찾기
SELECT * FROM sys.schema_redundant_indexes;
💡

이 두 뷰를 알고 있으면 "인덱스 정리를 어떻게 했나"에 구체적으로 답할 수 있습니다.

그리고 "조회가 느려서 인덱스를 추가했는데 쓰기가 느려져서 다시 검토했다"는 서사가 있으면 인덱스를 저울질로 이해하는 사람으로 읽힙니다.

08

OFFSET 1000000이 느린 이유와 실전 해결책

거의 모든 서비스가 겪는 문제라 면접관이 공감하는 지점입니다. 커서 기반을 언급하면 실무 경험으로 읽힙니다.

OFFSET 방식

SELECT * FROM orders
 ORDER BY id DESC
 LIMIT 20 OFFSET 1000000;
읽고 버린 행 0 읽고 버린 행 480,000 읽고 버린 행 1,000,000 필요한 행 20

OFFSET은 앞의 100만 행을 실제로 읽고 버립니다. 뒤 페이지로 갈수록 선형으로 느려집니다.

커서 기반 (No Offset)

SELECT * FROM orders
 WHERE id < :last_seen_id
 ORDER BY id DESC
 LIMIT 20;
읽고 버린 행 0 읽고 버린 행 0 필요한 행 20

마지막으로 본 id부터 인덱스를 바로 찾아 들어갑니다. 몇 번째 페이지든 같은 비용입니다. 

-- 페이지 번호 UI를 꼭 유지해야 하면: 커버링 인덱스로 PK만 먼저 뽑고 조인 (deferred join)
SELECT o.* FROM orders o
  JOIN (SELECT id FROM orders ORDER BY id DESC LIMIT 20 OFFSET 1000000) t
    ON o.id = t.id;
-- 서브쿼리는 인덱스만 읽어서(커버링) 100만 행을 훑는 비용이 훨씬 싸다

01둘 다 "20건"을 가져오는 같은 목적의 쿼리입니다.

02왼쪽은 버릴 행을 계속 읽습니다. 오른쪽은 인덱스로 바로 위치를 찾습니다.

03100만 행을 읽고 버린 뒤에야 20건을 반환합니다. 이게 OFFSET의 비용입니다.

04페이지 번호 UI가 필요하면 deferred join이 절충안입니다.

💡

커서 기반의 트레이드오프도 같이 말하면 완성됩니다.

"3페이지로 점프"가 안 되고, 정렬 기준이 유니크하지 않으면 (created_at, id) 같은 복합 커서가 필요합니다. 무한 스크롤·앱 목록에는 커서, 관리자 페이지 번호 UI에는 deferred join이 현실적인 선택입니다.

도구

EXPLAIN — 최소한 type과 Extra는 즉시 해석할 수 있어야 한다

EXPLAIN SELECT * FROM orders WHERE status = 'PAID';
EXPLAIN FORMAT=JSON SELECT ...;   -- 비용 정보까지 상세히
EXPLAIN ANALYZE SELECT ...;       -- 8.0.18+. 실제로 실행하고 실측 시간을 보여준다

type — 접근 방식. 위에서 아래로 좋다

system, const행 1개. PK/UNIQUE 등호. 최고
eq_ref조인에서 PK/UNIQUE로 1행씩 매칭
ref비유니크 인덱스 등호. 일반적으로 양호
range인덱스 범위 스캔. BETWEEN, >, IN
index인덱스 풀 스캔
ALL테이블 풀 스캔. 튜닝 대상 1순위

Extra — 정보량이 가장 많다

Using index커버링 인덱스. 좋다
Using where인덱스로 못 걸러낸 조건을 서버에서 추가 필터링
Using index conditionICP. 스토리지 엔진에서 미리 필터. 좋다
Using filesort정렬을 별도로 수행
Using temporary임시 테이블 생성. 무겁다
Using join buffer조인 대상에 인덱스가 없다

핵심 컬럼

key
실제로 사용된 인덱스. NULL이면 인덱스를 안 썼다
possible_keys
후보. 여기 있는데 key가 NULL이면 옵티마이저가 일부러 버린 것
rows
읽을 것으로 예상되는 행 수 (추정치)
filtered
rows 중 조건을 통과할 비율(%). rows × filtered가 실제 결과 규모
key_len
사용된 인덱스의 바이트 길이. 복합 인덱스에서 몇 번째 컬럼까지 썼는지 알 수 있다

튜닝 순서 (실무 답변용)

  1. 느린 쿼리를 찾는다 — slow query log, performance_schema
  2. EXPLAIN으로 type과 Extra를 본다
  3. ALL·filesort·temporary가 보이면 인덱스 후보를 세운다
  4. 추가하고 EXPLAIN ANALYZE로 실측 전후를 비교한다
  5. 쓰기 성능과 디스크 사용량 영향을 확인한다
  6. 인덱스로 안 되면 쿼리를 다시 쓴다 (서브쿼리→조인, N+1 제거, 커서 페이지네이션)
-- 느린 쿼리 상위 10개
SELECT DIGEST_TEXT, COUNT_STAR, AVG_TIMER_WAIT/1000000000 AS avg_ms
  FROM performance_schema.events_statements_summary_by_digest
 ORDER BY AVG_TIMER_WAIT DESC
 LIMIT 10;
💡

Using filesort가 "파일에 정렬한다"는 뜻은 아닙니다.

데이터가 작으면 메모리에서 정렬합니다. 이걸 알고 있으면 좋습니다.

정리

락과의 연결까지 가면 차별화된다

인덱스는 데이터를 정렬된 자료구조로 따로 유지해서 풀 스캔을 피하게 해주는 장치입니다. InnoDB는 B+Tree를 쓰고, 데이터가 리프에만 있어 트리가 낮고 리프가 연결돼 있어 범위 조회와 정렬에 강합니다. 클러스터드(PK)는 리프가 곧 행이고, 세컨더리는 리프에 PK만 있어서 조회가 2단계가 됩니다. 그 2단계를 없애는 게 커버링 인덱스이고, 증거는 Using index입니다. 복합 인덱스는 왼쪽부터 연속으로만 쓰이고, 등호를 앞·범위를 뒤에 둡니다. 인덱스를 못 타는 건 대체로 정렬 순서를 쓸 수 없게 만들었을 때입니다. 그리고 인덱스는 공짜가 아니라 쓰기 비용과 디스크를 냅니다.

InnoDB의 락은 행이 아니라 인덱스 레코드에 걸립니다.

status에 인덱스가 없으면 UPDATE orders SET status='DONE' WHERE status='PENDING'는 풀 스캔하면서 스캔한 모든 행에 락을 겁니다. 테이블 전체가 잠긴 것과 같아집니다. 그래서 인덱스는 성능 도구이면서 동시에 동시성 도구입니다. 트랜잭션 편 08장면과 이어집니다.

자주 하는 실수

  • "인덱스는 조회를 빠르게 한다"에서 멈춘다 → 쓰기 비용, 안 타는 경우, 락 관계까지가 한 세트입니다
  • 클러스터드/세컨더리 구분을 못 한다 → InnoDB 인덱스 이해의 기준선입니다
  • 복합 인덱스를 "컬럼 여러 개에 각각 인덱스 거는 것"으로 오해한다
  • EXPLAIN을 읽을 줄 모른다 → 최소한 type과 Extra는 즉시 해석해야 합니다
  • 개선 경험을 "인덱스 걸어서 빨라졌다"로만 말한다 → 전후 수치를 준비합니다. "2.3초에서 40ms로 줄었습니다" 같은 숫자 하나가 답변의 무게를 바꿉니다
