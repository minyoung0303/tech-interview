09 · Read Replica / Sharding

DB 확장
복제는 읽기를, 샤딩은 쓰기를 확장한다

둘을 "DB 확장 방법"으로 뭉치면 답이 흐려집니다. Read Replica는 같은 데이터를 복사해서 읽기를 나누고, 샤딩은 데이터를 쪼개서 쓰기와 용량까지 나눕니다. 확장하는 축이 다릅니다. 그리고 샤딩은 마지막 수단입니다.

Read Replica 복제 지연 샤드 키 크로스 샤드 7장면
01 축이 다르다 02 복제 지연 03 방금 쓴 값 04 읽기 라우팅 05 샤드 키 06 잃는 것 07 순서 비교표 정리
01

같은 데이터를 복사하는가, 데이터를 쪼개는가

Read Replica는 모든 노드가 전체 데이터를 갖습니다. 그래서 읽기만 늘어납니다. 샤딩은 노드마다 일부 데이터만 갖습니다. 그래서 쓰기와 용량이 함께 늘어납니다.

Read Replica — 같은 데이터를 복사

쓰기 100% 읽기 분산
Primary전체 데이터
Replica 1전체 데이터
Replica 2전체 데이터
Replica 3전체 데이터

쓰기는 여전히 Primary 한 대가 전부 받는다 데이터가 노드 수만큼 중복 저장된다

샤딩 — 데이터를 쪼갠다

쓰기 + 읽기
라우팅 계층샤드 키 = user_id
Shard 0user 0 – 249
Shard 1user 250 – 499
Shard 2user 500 – 749
Shard 3user 750 – 999

쓰기가 4개로 나뉜다 저장 용량도 4배 대신 조인·트랜잭션·집계가 어려워진다

Primary전체
Replica 1전체 (사본)
Shard 01/4

01DB 한 대가 쓰기와 읽기를 모두 받고 있습니다. 조회가 늘어 버티기 어려워졌습니다.

02Read Replica를 붙입니다. Primary의 데이터를 복제해서 읽기를 여러 노드로 분산합니다. 앱 변경은 "조회는 Replica로" 정도라 작습니다.

03그런데 쓰기는 여전히 Primary 한 대가 전부 받습니다. 그리고 데이터는 노드마다 전체가 중복 저장됩니다. 저장 용량 문제는 전혀 해결되지 않았습니다.

04샤딩은 접근이 다릅니다. 샤드 키를 정하고 데이터 자체를 나눠 담습니다.

05그러면 쓰기도 용량도 노드 수만큼 늘어납니다. 대신 여러 샤드에 걸친 조인·트랜잭션·집계가 어려워집니다. 대가가 큽니다.

💡

"Read Replica를 늘리면 쓰기도 빨라지나요?" — 아닙니다.

오히려 약간 느려질 수 있습니다. Primary는 자기 쓰기 작업 외에 binlog를 만들고 Replica들에게 전송하는 부담을 추가로 집니다. 준동기 복제까지 쓰면 최소 1개 Replica가 받았음을 확인한 뒤 커밋하므로 쓰기 지연이 명확히 늘어납니다. "읽기 확장 전용"이라는 걸 정확히 말하는 게 이 질문의 절반입니다.

02

복제는 비동기다 — 그래서 지연이 생긴다

Primary는 binlog에 쓰고 바로 클라이언트에 성공을 응답합니다. Replica가 그걸 받아 적용하는 건 그 다음 일입니다.

1Primary가 트랜잭션을 커밋하고 binlog에 기록한다
2여기서 이미 클라이언트에 "성공"을 응답한다 — 비동기 복제의 핵심
3Replica의 I/O 스레드가 binlog를 받아 relay log에 쓴다
4Replica의 SQL 스레드가 relay log를 실행한다 ← 여기가 병목
5이제야 Replica에서 조회 가능. 그 사이가 복제 지연(replication lag)
0.0초 · Seconds_Behind_Source
평시

지연이 폭발하는 원인

  • 대량 UPDATE/DELETE 한 방 — UPDATE … WHERE로 100만 행
  • 긴 트랜잭션, 큰 DDL
  • Replica 사양이 Primary보다 낮음
  • MySQL 5.x의 단일 스레드 적용 (8.0은 병렬 워커)
  • Replica에서 무거운 분석 쿼리를 돌려 SQL 스레드가 밀림

확인과 완화

-- 지연 확인 (MySQL 8.0)
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source: 12

-- 병렬 적용 활성화
replica_parallel_workers = 8
replica_parallel_type   = LOGICAL_CLOCK

대량 변경은 배치로 쪼개서 실행합니다. 한 번에 100만 행 대신 1만 행씩 100번. 이게 실무 습관입니다.

01Primary가 커밋하고 binlog에 씁니다. 그리고 바로 클라이언트에 성공을 응답합니다. Replica를 기다리지 않습니다.

02Replica의 I/O 스레드가 binlog를 받아 relay log에 씁니다. 여기는 보통 빠릅니다.

03SQL 스레드가 relay log를 실제로 실행합니다. 여기가 병목입니다. 큰 UPDATE 한 방이 오면 이 단계에서 몇 분씩 밀립니다.

04지연이 커지는 동안 Replica는 과거를 보여줍니다. 앱은 아무 에러도 받지 않습니다. 그래서 알아채기 어렵습니다.

05원인은 대체로 대량 변경 한 방입니다. 그래서 대량 작업은 배치로 쪼개고, Seconds_Behind_Source를 모니터링에 걸어둡니다.

03

가장 자주 겪는 사고 — 방금 저장한 값이 안 보인다

Read Replica의 존재는 누구나 압니다. 복제 지연을 어떻게 다루는지를 말할 수 있으면 이 질문은 통과입니다.

쓰기는 Primary로 갔고 성공했다 리다이렉트된 조회는 Replica로 갔다 → 예전 값 잠시 뒤 복제가 끝나면 정상으로 보인다 대응은 네 가지
대응설명

중요 읽기는 Primary로결제·잔액·방금 쓴 데이터 조회는 Primary에서. 가장 흔한 해법
쓰기 후 N초 Primary 고정세션에 쓰기 시각을 기록하고 그 사용자만 일정 시간 Primary로 (sticky read)

01사용자가 프로필 이름을 "홍길동"으로 수정합니다.

02쓰기는 Primary로 가서 정상 커밋되고 200을 응답합니다. 여기까지 아무 문제 없습니다.

03앱이 프로필 페이지로 리다이렉트합니다. 이 조회는 Replica로 갑니다. 그런데 복제가 아직 안 끝났습니다.

04사용자는 예전 이름을 봅니다. 앱은 에러를 안 냈고 로그도 깨끗합니다. 문의만 들어옵니다.

05몇백 밀리초 뒤 복제가 끝나면 정상으로 보입니다. 재현이 어려운 버그가 되는 이유입니다.

06대응은 네 가지입니다. 실무에서 가장 깔끔한 건 쓰기 응답에 갱신된 객체를 담아서 재조회 자체를 없애는 것입니다.

SELECT라고 무조건 Replica로 보내면 안 됩니다.

트랜잭션 안의 SELECT는 Primary로 가야 합니다. 같은 트랜잭션에서 쓴 값을 읽어야 하고, SELECT … FOR UPDATE는 락이 필요하기 때문입니다. 쿼리 문자열만 보고 자동 분기하는 프록시 설정에서 이 사고가 납니다.

04

읽기 라우팅을 어디서 하나

Replica를 붙이는 건 클릭 몇 번인데, "어떤 쿼리를 어디로 보낼지" 결정하는 지점이 실제 작업량입니다.

A 애플리케이션에서 — 커넥션을 writer/reader 두 개 만들고 코드에서 고른다. 가장 명시적이고 제어가 정확하다. 트랜잭션 안은 무조건 writer로 강제할 수 있다
B Aurora Reader Endpoint — 여러 Replica로 자동 분산해주는 엔드포인트. 앱은 주소 두 개만 알면 된다
C RDS Proxy / ProxySQL — 프록시가 쿼리를 보고 자동 분기하고 커넥션도 풀링한다. 앱 변경이 가장 적다. 대신 자동 분기의 오판을 주의해야 한다
D ORM / 프레임워크 설정 — 편하지만 트랜잭션 경계 처리를 반드시 확인한다 
// 애플리케이션 라우팅 — 의도가 코드에 남는다
type DB struct {
    W *sql.DB   // writer  : Primary
    R *sql.DB   // reader  : Replica (또는 Reader Endpoint)
}

// 목록 조회 — 약간 과거여도 괜찮다
rows, _ := db.R.Query("SELECT id, name FROM users LIMIT 20")

// 결제 직전 잔액 확인 — 반드시 최신이어야 한다
var balance int64
db.W.QueryRow("SELECT balance FROM accounts WHERE id = ?", id).Scan(&balance)

// 트랜잭션은 항상 writer
tx, _ := db.W.Begin()
판단 기준: 이 조회가 몇 초 과거여도 괜찮은가

01가장 명시적인 방법은 앱에서 커넥션을 두 개 두고 직접 고르는 것입니다. 의도가 코드에 남습니다.

02Aurora를 쓰면 Reader Endpoint가 Replica 분산을 대신해줍니다.

03RDS Proxy나 ProxySQL은 프록시가 자동 분기합니다. 앱 변경이 적은 대신 오판 위험이 있습니다.

04어느 방법이든 판단 기준은 하나입니다 — "이 조회가 몇 초 과거여도 괜찮은가." 목록은 괜찮고 잔액은 안 됩니다.

05

샤딩은 샤드 키 선택이 전부다

잘못 정하면 핫스팟이 생기고, 나중에 바꾸려면 전체 데이터를 재배치해야 합니다. 되돌리기가 가장 어려운 결정입니다.

① 레인지 샤딩 — user_id 구간으로 나눈다

Shard 0user 0 – 249
Shard 1user 250 – 499
Shard 2user 500 – 749
Shard 3user 750 – 999
초기에는 고르게 나뉜다 신규 가입자는 전부 마지막 샤드로 → 핫스팟 해시 샤딩으로 바꾸면 균등해진다 그런데 노드를 4 → 5로 늘리면 거의 전부 재배치 해법: 논리 샤드를 물리 노드보다 많이 만든다 이제 노드 추가는 논리 샤드 이동으로 끝난다

논리 샤드 (실무 정석)

logical_shard = hash(user_id) % 1024     // 논리 샤드 1024개 — 절대 안 바꾼다
physical_node = shard_map[logical_shard]      // 매핑만 바꾼다

// 노드 4대 → 8대로 늘릴 때
// 논리 샤드 256개씩 → 128개씩. 해시 재계산이 필요 없다

논리 샤드 1024개를 만들고 물리 노드 4대에 256개씩 배치합니다. 노드를 늘릴 때 논리 샤드 단위로만 옮기면 되므로 해시를 다시 계산하지 않습니다. 이걸 말하면 확실히 눈에 띕니다.

방식설명문제
레인지user_id 0~999 → 샤드 0신규가 마지막 샤드로 쏠린다 (핫스팟)
해시hash(user_id) % N균등하지만 N이 바뀌면 거의 전부 재배치
일관된 해싱 / 논리 샤드해시 링 또는 고정 논리 샤드 → 노드 매핑이동량이 적다. 실무 정석
디렉터리매핑 테이블을 따로 관리유연하지만 매핑 테이블이 SPOF/병목

01레인지 샤딩입니다. user_id 구간으로 4등분했습니다. 초기에는 고르게 보입니다.

02서비스가 자라면서 신규 가입자가 계속 들어옵니다. ID가 큰 사용자는 전부 마지막 샤드로 갑니다. 그리고 활동량이 많은 최근 사용자가 거기 몰려 있습니다 — 핫스팟입니다.

03해시 샤딩으로 바꾸면 균등하게 흩어집니다. 문제가 해결된 것 같습니다.

04그런데 노드를 4대에서 5대로 늘리면 % 4가 % 5가 되어 거의 모든 데이터의 위치가 바뀝니다. 리샤딩 지옥입니다.

05그래서 논리 샤드를 물리 노드보다 훨씬 많이 만듭니다. 해시는 논리 샤드 번호를 정하고, 논리 샤드 → 노드 매핑만 따로 관리합니다.

06이제 노드 추가는 논리 샤드 몇 개를 옮기는 작업이 됩니다. 해시 재계산이 없습니다. 방식별 트레이드오프를 정리하면 표와 같습니다.

💡

샤드 키는 "쿼리 패턴"으로 정합니다.

대부분의 조회가 WHERE user_id = ?로 들어온다면 user_id가 샤드 키여야 합니다. 그러면 대부분의 쿼리가 단일 샤드에서 끝납니다. 반대로 샤드 키가 아닌 조건으로 조회하면 모든 샤드에 질의(scatter-gather)해야 해서 샤딩이 오히려 느려집니다. "샤드 키가 아닌 조건으로 조회하면 어떻게 되나요?"는 이 주제의 핵심 꼬리질문입니다. 대안은 보조 인덱스 테이블을 따로 두거나, 검색은 Elasticsearch로 분리하는 것입니다.

06

샤딩하면 잃는 것들 — 이걸 말할 수 있어야 한다

샤딩을 쉽게 말하는 게 가장 큰 감점 요인입니다. DB가 대신 해주던 일들이 전부 애플리케이션 책임으로 넘어옵니다.

단일 DB에서는 당연했던 것

-- 조인
SELECT u.name, o.amount
  FROM users u JOIN orders o ON o.user_id = u.id
 WHERE o.created_at >= '2026-01-01';

-- 트랜잭션
BEGIN;
  UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
  UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
COMMIT;

-- 유니크 제약 / 집계 / 페이지네이션
UNIQUE KEY uk_email (email)
SELECT COUNT(*) FROM orders;
SELECT * FROM orders ORDER BY id DESC LIMIT 20;

샤딩 후

✕크로스 샤드 조인 — 불가능. 앱에서 두 번 조회해 합치거나, 비정규화해서 같은 샤드에 둔다
✕크로스 샤드 트랜잭션 — ACID가 깨진다. Saga 패턴이나 결과적 일관성을 받아들인다
✕전역 유니크 제약 — DB가 이메일 유니크를 보장하지 못한다. 별도 유니크 인덱스 테이블 필요
✕AUTO_INCREMENT — 샤드마다 1부터 시작한다. Snowflake / UUID v7 / ULID 필요
✕전체 집계·정렬 — 모든 샤드에서 가져와 앱에서 병합해야 한다
✕페이지네이션 — 특히 어렵다. 커서 기반으로 바꾸고 샤드별 커서를 관리
✕스키마 변경 · 백업 · 모니터링 — 샤드 수만큼 곱해진다

장애 양상도 달라집니다.

Read Replica는 Replica 하나가 죽어도 서비스가 유지됩니다(읽기를 다른 곳으로 보내면 됩니다). 샤딩은 샤드 하나가 죽으면 그 범위의 사용자만 완전히 장애입니다. "전체 다운은 아니지만 일부는 아무것도 못 한다" — 대응 방식이 다릅니다. 그래서 실무에서는 샤드마다 다시 Replica를 붙입니다. 노드 수가 곱셈으로 늘어납니다.

01왼쪽은 단일 DB에서 아무 생각 없이 쓰던 쿼리들입니다. 오른쪽은 샤딩 후 각각 어떻게 되는지입니다.

02크로스 샤드 조인과 트랜잭션이 먼저 깨집니다. 계좌 이체 두 줄이 분산 트랜잭션 문제가 됩니다.

03유니크 제약과 AUTO_INCREMENT도 못 씁니다. PK 생성기를 따로 만들어야 합니다.

04집계와 페이지네이션이 애플리케이션 책임이 됩니다. ORDER BY … LIMIT 20 하나가 모든 샤드 조회 + 병합이 됩니다.

05운영 부담도 샤드 수만큼 곱해집니다. 그래서 샤딩은 마지막 수단입니다. 다음 장면에서 순서를 봅니다.

💡

파티셔닝과 샤딩의 차이도 자주 묻습니다.

파티셔닝은 하나의 DB 서버 안에서 큰 테이블을 물리적으로 나누는 것입니다. 목적은 관리 편의(오래된 파티션 일괄 삭제)와 파티션 프루닝이고, 서버 자원은 그대로입니다. 샤딩은 여러 DB 서버로 분산해서 자원 자체를 늘리는 것입니다. 한 줄로 정리하면 "샤딩은 수평 분할을 여러 서버로 확장한 것"입니다.

07

순서를 말할 수 있으면 판단력으로 읽힌다

"DB가 느립니다"에 바로 샤딩을 꺼내면 감점입니다. 싼 것부터, 되돌릴 수 있는 것부터입니다.

01인덱스 · 쿼리 튜닝 — 대부분 여기서 끝난다. 2.3초 → 40ms가 흔하다 (인덱스 편)
02N+1 제거, 커넥션 풀 조정
03캐시 — Redis, CDN. 읽기 부하는 Replica보다 캐시가 먼저인 경우가 많다
04Scale-up — 인스턴스 사양 상향. 시간을 버는 카드 (스케일 편)
05Read Replica — 읽기 분리. 복제 지연을 다룰 준비가 필요하다
06아키텍처 변경 — 비동기화(SQS), CQRS, 검색은 Elasticsearch로 분리
07파티셔닝 · 오래된 데이터 아카이빙 — 테이블을 물리적으로 줄인다
08샤딩 — 마지막. 되돌리기가 가장 어렵다
여기까지가 가장 싸고 효과가 크다 대부분의 서비스는 여기서 충분하다 여기부터는 설계 변경이다 샤딩은 데이터 증가율과 쓰기 부하를 근거로 판단할 문제

01먼저 인덱스와 쿼리를 봅니다. 대부분 여기서 끝나고, 가장 쌉니다. 측정 없이 다음 단계로 가지 않습니다.

02그다음 캐시와 Scale-up입니다. 읽기 부하라면 Replica보다 캐시가 먼저인 경우가 많습니다 — DB까지 안 가는 게 가장 빠릅니다.

03Read Replica로 읽기를 분리합니다. 대부분의 서비스는 여기서 충분합니다. 대신 복제 지연을 다룰 준비가 필요합니다.

04그다음은 설계 변경입니다 — 비동기화, CQRS, 검색 분리, 파티셔닝, 아카이빙.

05샤딩은 마지막입니다. "저희 규모에서는 5번까지로 대부분 해결된다고 보고, 샤딩은 데이터 증가율과 쓰기 부하를 근거로 마지막에 판단할 문제라고 생각합니다" — 이 톤이 실무 판단력으로 읽힙니다.

정리

이 7장면을 한 문단으로

확장하는 축이 다릅니다. Read Replica는 같은 데이터를 복제해서 읽기를 분산합니다. 도입은 쉽지만 쓰기는 여전히 Primary 한 대가 받고, 비동기 복제라서 복제 지연이 생깁니다. 그래서 방금 쓴 값이 안 보이는 read-after-write 문제를 다뤄야 하고, 가장 깔끔한 해법은 쓰기 응답에 갱신된 객체를 담아 재조회를 없애는 것입니다. 트랜잭션 안의 SELECT는 항상 Primary로 보냅니다. 샤딩은 데이터를 쪼개서 쓰기와 용량까지 확장하지만, 샤드 키를 정해야 하고(쿼리 패턴 기준, 핫스팟 주의, 논리 샤드 권장) 크로스 샤드 조인·트랜잭션·유니크 제약·집계·페이지네이션을 잃습니다. 그래서 순서가 있습니다 — 인덱스·쿼리 → 캐시 → Scale-up → Read Replica → 아키텍처 변경 → 마지막에 샤딩입니다.

자주 하는 실수

  • 둘을 "DB 확장 방법"으로 뭉쳐서 말한다 → 읽기 확장 vs 쓰기 확장이 핵심 구분
  • Read Replica의 복제 지연을 언급하지 않는다 → 실무에서 가장 자주 부딪히는 문제
  • 샤딩을 쉽게 말한다 → 잃는 것을 말할 수 있어야 한다
  • 순서 없이 바로 샤딩을 답한다 → 판단력이 없어 보인다
  • Replica를 늘리면 쓰기도 빨라진다고 생각한다 → 오히려 Primary 부담이 늘어난다
  • 모든 SELECT를 Replica로 보낸다 → 트랜잭션 내부와 방금 쓴 데이터는 Primary
  • 파티셔닝과 샤딩을 구분하지 못한다
