## 0. 먼저 정할 것 — 2주로는 무엇이 되고 무엇이 안 되는가

**된다**
- 자주 나오는 **8개 유형**을 보고 알아채는 것
- 각 유형의 **템플릿을 손에 붙이는 것** (외워서 바로 타이핑)
- 시간복잡도로 **알고리즘을 역산하는 것**
- 쉬움~중간 난이도(백준 실버~골드5, 프로그래머스 Lv.2)를 **안정적으로** 푸는 것

**안 된다**

> 요일 배분은 [README 의 하루 루프](../README.md#하루-루프)가 기준이다 —
> **월·화·목·금이 알고리즘 데이**, 수는 CS 노트, 토는 면접, 일은 정산이다.
>

> 얕게 14개보다 제대로 10개가 낫다. 시간이 부족하면 ⭐ 표시한 Day 를 우선한다.

**이 순서를 그대로 반복한다. 순서를 지키는 게 내용보다 중요하다.**

| 시간 | 블록 | 하는 일 |

| 0:20 – 0:45 | **개념 + 템플릿** | 그날 유형의 개념을 읽고 `templates/`의 템플릿을 **손으로 다시 타이핑**. 복붙 금지 |

| 1:45 – 2:00 | **해설과 대조** | 못 푼 것, 푼 것 모두 다른 사람 풀이와 비교. **더 짧은 방법이 있었는지** 본다 |
| 마감 10분 | **오답 노트 + 커밋** | 아래 4줄만 쓴다. 5분 넘기지 않는다 |

### 오답 노트는 딱 4줄

```
문제: 백준 2178 미로 탐색
유형: BFS (최단거리)
막힌 지점: 방문 처리를 큐에 넣을 때가 아니라 꺼낼 때 했다 → 중복 삽입으로 TLE
다음에 할 것: BFS는 "큐에 넣는 순간 visited 표시"를 조건반사로
```

**"다음에 할 것"이 핵심이다.** 감상이 아니라 **행동 규칙**으로 쓴다.
이 한 줄이 다음에 같은 실수를 막는다.

### 재풀이 스케줄 (이게 2주 압축의 핵심)

틀린 문제는 **3번 다시 푼다.**

```
D+0  틀림 → 해설 보고 이해 → 오답 노트
D+1  코드 안 보고 다시 풀기        ← 여기서 대부분 또 막힌다. 정상이다
D+3  다시 풀기
D+7  다시 풀기 → 여기서 막히면 "아직 내 것이 아니다"
```

**새 문제 3개보다 틀린 문제 1개 재풀이가 점수를 더 올린다.**
2주짜리 계획에서 이걸 빼면 그냥 문제 구경이 된다.

## 2. 문제 푸는 절차 7단계 — 이게 "문제 푸는 방식"이다

**코드를 바로 치지 않는다. 종이(또는 주석)에 먼저 쓴다.**
이 절차 자체를 14일 동안 몸에 붙이는 게 이 계획의 진짜 목표다.

```python
"""
1) 입력/출력 확정      N, M 범위 / 자료형 / 출력 형식(개수? 값? 경로?)
2) 제한으로 역산       N ≤ 1000 이면 O(N²) 가능, N ≤ 10만이면 O(N log N)까지
3) 유형 판정           최단거리? 최적값? 조합? 구간? 정렬 후 순회?
4) 자료구조 선택       list / deque / heapq / set / dict / 2차원 배열
5) 손으로 예제 1개     반드시 종이에서 한 번 돌린다. 여기서 오해가 걸러진다
6) 코드               템플릿을 먼저 깔고 문제 조건만 채운다
7) 반례 점검           N=1, 빈 입력, 최댓값, 음수, 중복, 시작=도착
"""
```

### 3단계 유형 판정 — 문장에서 유형을 찾는 신호

| 문제에 이런 말이 있으면 | 거의 확정 |
|---|---|
| "**최소 몇 번**", "최단 거리", "최소 이동" + 가중치 없음 | **BFS** |
| 최단 거리 + **가중치 있음** | **다익스트라** |
| "모든 경우", "**가능한 조합**", "순서대로 뽑아" | **백트래킹 / 순열·조합** |
| "**최댓값 / 최솟값**"인데 선택이 앞의 선택에 의존 | **DP** |
| "**최대 개수**"인데 정렬하면 답이 보임 (회의실, 동전) | **그리디** |
| "**연속된 구간**", "부분 수열의 합" | **투 포인터 / 슬라이딩 윈도우 / 누적합** |
| "**~ 이하가 되도록 하는 최댓값**", "K개로 나눌 수 있는 최소" | **파라메트릭 서치(이분 탐색)** |
| "**가장 가까운 큰 값**", "괄호", "되돌리기" | **스택** |
| "**K번째**", "매번 가장 작은 것" | **힙** |
| "**연결되어 있는지**", "같은 그룹인지" | **유니온 파인드 / DFS** |
| "**순서를 정해라**" + 선후 관계 | **위상 정렬** |
| "**찾기**"만 반복 (존재 여부) | **set / dict** — 정렬+이분탐색보다 먼저 고려 |
| 시키는 대로만 하면 됨, 격자 이동, 회전 | **구현/시뮬레이션** |

**이 표를 첫날에 한 번 읽고, 매일 문제 풀기 전에 훑는다.**

### 2단계 제한 역산표 — 외워두면 30초 만에 방향이 잡힌다

**보통 1초에 파이썬은 약 1,000만~2,000만 번 연산**으로 잡는다 (PyPy면 더 여유).

| N의 크기 | 허용 복잡도 | 쓸 수 있는 것 |
|---|---|---|
| N ≤ 10 | O(N!) | 완전 순열, 백트래킹 |
| N ≤ 25 | O(2^N) | 부분집합 전체 탐색, 비트마스크 |
| N ≤ 500 | O(N³) | 플로이드 워셜, 3중 루프 |
| N ≤ 5,000 | O(N²) | 2중 루프 DP, 완전 탐색 |
| N ≤ 100,000 | **O(N log N)** | 정렬, 이분 탐색, 힙, 다익스트라 |
| N ≤ 1,000,000 | **O(N)** | 투 포인터, 누적합, 한 번 순회 |
| N ≤ 10^12 이상 | O(log N) | 이분 탐색, 수학 공식 |

> **N이 10만인데 2중 루프를 떠올렸다면 그 접근은 버린다.** 고민을 아끼는 가장 빠른 방법이다.

## 3. 20분 룰 — 단기 학습에서 가장 중요한 규칙

```
0 ~ 20분   혼자 고민한다. 종이에 그린다
20 ~ 25분  힌트만 본다 (유형 이름, 첫 접근만)
25분       그래도 안 되면 해설을 본다 → 이해하고 → 닫고 → 처음부터 타이핑
```

**2주짜리 계획에서 한 문제에 1시간 쓰는 건 손해다.**
"고민하는 힘"은 장기 훈련에서 길러진다. 지금은 **패턴 흡수 속도**가 목표다.

단, 해설을 본 문제는 **반드시 그날 코드를 닫고 처음부터 다시 친다.**
읽어서 이해한 것과 쓸 수 있는 것은 완전히 다르다. 이 구분이 실력이다.

## 5. 모의 테스트 운영법 (Day 7 · Day 14)

**실제 시험과 같은 조건으로 한다. 이게 없으면 "풀 줄은 아는데 시험에서 못 푸는" 상태가 된다.**

```
준비   90분 타이머 · 문제 3개 (쉬움 1, 중간 2) · 처음 보는 문제
금지   검색, 이전 코드 열어보기, 자동완성 참고
허용   내가 만든 templates/ 폴더 (실제 시험에서도 머리에 있는 것이니까)

진행   1) 3문제를 먼저 다 읽고 난이도 순서를 정한다   ← 이 습관이 점수를 만든다
       2) 쉬운 것부터 확실히 끝낸다
       3) 한 문제에 30분 넘어가면 넘어간다. 미련 없이

종료 후 (30분)
       각 문제를 "왜 못 풀었나"로 분류한다
         A. 유형을 못 알아봤다      → 2단계 유형 판정표 다시
         B. 유형은 알았는데 구현 실패 → 템플릿 재타이핑
         C. 시간 초과              → 복잡도 역산 훈련
         D. 반례                  → 7단계 반례 체크리스트
```

**분류가 다음 주 계획을 결정한다.** A가 많으면 유형 판정, B가 많으면 템플릿을 더 친다.

## 6. 막혔을 때 체크리스트 (20분 안에 훑는다)

- [ ] 문제를 **한 문장으로** 다시 말할 수 있나? 못 하면 아직 이해를 못 한 것이다
- [ ] N의 최댓값을 봤나? 복잡도 역산을 했나?
- [ ] **완전 탐색으로는 몇 번**인가? 그게 되면 그냥 완전 탐색으로 푼다
- [ ] 예제 입력을 **손으로** 한 번 돌려봤나?
- [ ] 정렬하면 단순해지나?
- [ ] 이걸 그래프로 볼 수 있나? (정점과 간선이 무엇인지 대응시켜 본다)
- [ ] "최소 횟수"인가? → BFS
- [ ] 뒤에서부터 생각하면 쉬워지나? (DP는 자주 그렇다)
- [ ] 비슷한 문제를 **오답 노트에서** 본 적 있나?

## 7. 파이썬 함정 (2주 안에 반드시 겪는다)

**여기서 시간을 가장 많이 잃는다. 첫날 한 번 읽고 Day 7에 다시 읽는다.**

| 함정 | 대응 |
|---|---|
| `input()`이 느려서 시간 초과 | `input = sys.stdin.readline` **매번 첫 줄에 쓴다** (개행 포함되니 `.strip()` 주의) |
| 재귀 깊이 초과 (`RecursionError`) | `sys.setrecursionlimit(10**6)`. 깊이가 크면 **DFS를 스택으로 바꾼다** |
| `list.pop(0)`가 O(N) | `collections.deque` + `popleft()` |
| 문자열 `+=` 반복이 O(N²) | `list.append` 후 `''.join(...)` |
| `in` 연산자 — 리스트는 O(N) | 존재 확인은 **`set`** (O(1)) |
| 2차원 배열 얕은 복사 | `[[0]*m]*n` ❌ → `[[0]*m for _ in range(n)]` ✅ |
| `heapq`는 최소 힙만 | 최대 힙은 `-value`로 넣고 꺼낼 때 다시 부호 반전 |
| `sort()` vs `sorted()` | 전자는 제자리·`None` 반환, 후자는 새 리스트 |
| 음수 나눗셈 / 나머지 | `-7 // 2 == -4`, `-7 % 2 == 1`. C와 다르다 |
| 얕은 복사로 백트래킹 결과가 뭉개짐 | 결과 저장은 `result.append(path[:])` — **슬라이스 복사** |
| `int` 오버플로 걱정 | 파이썬은 없다. 대신 큰 수 연산이 느릴 수 있다 |
| `visited` 표시 시점 | BFS는 **큐에 넣을 때** 표시. 꺼낼 때 하면 중복 삽입으로 폭발 |
| 출력이 많아 느림 | `sys.stdout.write` 또는 결과를 모아 `print('\n'.join(...))` |
| `map` 객체를 두 번 못 씀 | 한 번 쓰면 소진된다. 필요하면 `list(map(...))` |

## 10. 면접 관점 — 알고리즘 질문은 이렇게 들어온다

실무 면접에서 알고리즘은 **코딩테스트와 다르게** 물어본다.
2주 공부가 끝나면 이 답도 준비해둔다.

| 질문 | 준비할 답의 방향 |
|---|---|
| "시간복잡도가 어떻게 되나요?" | **역산표를 근거로** 말한다. "N이 10만이라 O(N log N)까지 허용되어 정렬을 골랐습니다" |
| "이 코드를 더 빠르게 할 수 있나요?" | 자료구조 교체(list → set/dict), 중복 계산 제거(메모이제이션), 전처리(누적합) |
| "이 로직을 실무에서 쓴 적 있나요?" | 캐시 만료 처리(힙), 중복 제거(set), 페이지네이션 커서, 그래프 탐색으로 순환 참조 검사 |
| "DB 쿼리로도 되는데 왜 코드에서?" | 데이터 양, 트랜잭션 범위, DB 부하. → [index.md](../notes/database/db-index.md)와 연결 |
| "재귀 대신 반복으로 바꿀 수 있나요?" | 스택으로 명시적 변환. 파이썬 재귀 한도 이야기까지 |

> 코딩테스트용 알고리즘과 실무 면접용 알고리즘은 **같은 지식, 다른 질문**이다.
> 후자는 "왜 그걸 골랐나"를 묻는다. 그래서 **복잡도 역산 습관이 면접에서도 그대로 통한다.**
